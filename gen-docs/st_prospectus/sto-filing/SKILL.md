# 조각투자 증권신고서 (STO Filing)

조각투자 증권의 **유형 판정 → 신고서 작성 → 심사 검증**을 하나의 흐름으로 수행한다.

핵심 설계: 두 증권 유형은 문서 골격의 약 70%가 같다. 공통 부분은 `references/common-core.md`
하나로 관리하고, 유형별 파일은 **차이(델타)만** 담는다. 따라서 작성·검증 시
**항상 common-core.md를 먼저 읽고, 그 위에 유형별 파일을 덮어쓰는 방식**으로 동작한다.

---

## 왜 판정이 먼저인가

유형이 갈리면 문서 품질과 무관하게 **발행 가능 여부 자체가 갈린다.**

- 투자계약증권 → 사전 인허가 불요. 증권신고서만 제출하면 된다.
- 비금전신탁 수익증권 → 자본시장법 §110은 금전신탁 수익증권을 전제하므로,
  **혁신금융서비스 지정 없이는 발행 자체가 불가능하다.**
- 집합투자증권 → 집합투자업 인가 없이 발행하면 무인가 영업이다.

그래서 판정 없이 작성으로 넘어가면, 잘 쓴 신고서가 통째로 무의미해질 수 있다.
사용자가 "신고서 써줘"라고만 해도 판정을 건너뛰지 않는다.

---

## 실행 모드 — 기획 / 제출

정량 항목(재무·취득가·평가액·청약일정·수수료 등, 성격 F)은 초기 사업기획 단계에서
확정하기 어렵다. 그래서 두 모드로 나눈다. **모드는 착수 시 사용자에게 확인한다.**

- **기획 모드 (planning)** — 정량 F를 가정치로 채워 초안·심사까지 끝까지 돌려 사업
  아이디어를 빠르게 검증한다. 모든 가정치와 그로부터 나온 산출물에
  `[가정치·시뮬레이션 — 제출용 아님]`을 박고, 산출물 파일명 끝에 `_시뮬`을 붙인다.
- **제출 모드 (filing)** — 실측치만 쓴다. 없으면 `[미확정]`. 추측 금지 원칙 그대로.

기획 모드는 추측 금지의 **예외가 아니라 격리된 시뮬레이션**이다. 가정치는 별도 파라미터
시트(`references/common-core.md` §2.6)에만 들어가고, 워터마크 없이 신고서 본문에 사실처럼
쓰이는 순간 부실기재가 된다. 모드가 불명확하면 **제출 모드로 간주**한다.

## 워크플로우

### PHASE 1 — 유형 판정 (항상 수행)

`references/classification.md`를 읽고 STEP 0~5를 순서대로 수행한다.

사용자가 이미 유형을 단정했더라도(“투자계약증권으로 할 거예요”) **판정은 그대로 수행한다.**
다만 결과가 사용자 전제와 일치하면 간단히 확인만 하고 넘어가고, 어긋나면 그 사실을 먼저 알린다.

판정에 필요한 정보가 부족하면 **한 번에 몰아서** 묻는다. 항목을 하나씩 나눠 묻지 않는다.
사용자가 아직 상품 설계 단계라 답을 못 하는 항목은 `[미정]`으로 두고,
그 미정 항목이 판정을 뒤집을 수 있는지 여부를 명시한다.

**게이트 — 아래에 해당하면 PHASE 3으로 넘어가지 않는다**

| 상황 | 조치 |
|---|---|
| 집합투자증권에 해당 | 집합투자업 인가 필요를 알리고, 구조 재설계안을 제시한 뒤 중단 |
| 신탁수익증권인데 혁신금융서비스 미지정 | 지정 절차가 선행되어야 함을 알리고, 투자계약증권 구조로의 재설계 가능성을 검토한 뒤 중단 |
| 신탁수익증권인데 수탁자가 신탁업 미인가 | 동일하게 중단 |
| 판정 신뢰도 '낮음' | 법률의견서 또는 금융위 법령해석·비조치의견서 신청을 권고하고, 진행 시 잠정 판정임을 문서에 명시 |

중단이라고 해서 대화를 끝내지 않는다. 무엇을 바꾸면 진행 가능한지 구체적으로 제시한다.

### PHASE 2 — 입력 수집과 전문가 확장

정성 입력과 정량 입력을 나눠 진행한다. INPUT 블록을 raw로 통째 던지지 않는다.

**2a-i. 구조·정성 입력요청서.** 공통 INPUT + 판정된 유형의 델타 INPUT에서 **해당 유형과
기초자산 종류에 필요한 필드만** 추려, 우선순위(`필수·판정` / `필수·작성` / `권장`)와
성격(`F 사실` / `N 서술` / `J 판단`)과 미제공 시 영향을 표기한 **입력요청서**를 만든다.
형식은 `references/common-core.md` §2.5. 파일로 저장하고
(`입력요청서_<발행사>_YYYYMMDD.md`), 사용자는 인라인 답변 또는 채운 시트 제출 중 편한
쪽을 고른다. **PHASE 1에서 이미 받은 항목은 다시 묻지 않는다.**

**2a-ii. 정량 파라미터 시트.** 재무·취득가·평가액·발행수량·청약일정·수수료율 등
**정량 F 항목**은 신고서 본문과 분리해 별도 시트로 관리한다(형식·계산·모드 처리:
`references/common-core.md` §2.6). 제출 모드면 실측치를 요청하고, 기획 모드면 가정치로
채워 시뮬레이션한다. 시트의 값에서 단위 모집가액·스프레드 분해·수익률·시나리오가
파생되므로, 숫자를 바꾸면 관련 절이 자동으로 다시 계산된다.

**2b. 응답 수집.** 일부만 채워도 진행한다. 제출 모드에서 미응답 필수 F는
`[미확정: 확정 후 정정신고서 제출 예정]`으로, 기획 모드에서는 가정치로 채우고 워터마크한다.
최종 산출물 말미에 미확정·가정 목록을 모은다.

**2c. 전문가 확장.** 받은 답을 성격별로 처리한다(원칙: `common-core.md` §1의 F/N/J 표).
- **F(사실)** — 준 값(제출) 또는 가정치(기획)만 사용. 제출 모드에서 없으면 `[미확정]`.
  수치·일자·상대방·평가결과를 임의로 **지어내지 않는다.**
- **N(서술)** — 준 사실을 근거로 증권발행 전문가 수준으로 전개. 자산 종류가 주어지면 해당
  유형의 위험 카탈로그(common-core §4)를 적용하고, 이해상충·공시체계 등을 구조적으로 서술.
- **J(판단)** — 규제 기준과 사용자 사실로 초안을 제안하되 `[발행사 확인 요망]`을 붙인다.

이후 곧바로 PHASE 3으로 넘어가 전체 작성을 실행한다.

**없는 값을 지어내지 않는 것이 이 스킬의 최우선 규칙이다.** 제출 모드에서 확장은 사실의
함의를 전개하는 것이지 없는 사실을 만드는 것이 아니다. 기획 모드의 가정치는 파라미터 시트에
격리하고 워터마크(`[가정치·시뮬레이션 — 제출용 아님]`)를 유지한다. 워터마크 없이 본문에
사실처럼 기재되면 그 자체가 부실기재가 된다.

### PHASE 3 — 신고서 작성

1. `references/common-core.md` — 골격, 공통 작성 원칙, 공통 절 구성, 공통 위험군
2. 유형별 델타 파일 —
   - 투자계약증권 → `references/investment-contract.md`
   - 비금전신탁 수익증권 → `references/trust-beneficiary.md`

델타 파일은 공통 골격의 **특정 절을 대체하거나 추가**하는 방식으로 기술되어 있다.
공통 골격을 먼저 세운 뒤 델타를 적용한다.

산출물은 파일로 저장한다. 대화창에 전문을 쏟아내지 않는다.

### PHASE 4 — 자체 심사

작성 직후 **같은 턴에서** 심사를 수행한다. 사용자가 따로 요청하기를 기다리지 않는다.
방금 쓴 문서라도 심사역 관점으로 전환해서 읽는다.

심사 기준: `common-core.md`의 공통 매트릭스 + 유형별 델타 파일의 고유 매트릭스.
출력 형식(정정요구 카드, 심각도 등급)은 `common-core.md`에 정의되어 있다.

심사 태도의 핵심은 **선의로 읽지 않는 것**이다. 문구가 두 가지로 해석되면
투자자에게 불리한 해석을 기준으로 판정한다. 자기가 쓴 문서라고 봐주면 심사 단계가 무의미해진다.

## 부분 실행

사용자가 일부 단계만 원하면 그 단계만 수행한다. 다만 선행 정보가 없으면 최소한으로 확인한다.

| 사용자 요청 | 수행 |
|---|---|
| "이거 증권에 해당하나요" / "무슨 유형이죠" | PHASE 1만 |
| "뭐가 필요한지 알려줘" / "입력 항목만 정리해줘" | PHASE 1(유형 확인) → 2a만 (입력요청서 + 파라미터 시트) |
| "숫자는 대충 넣고 일단 돌려봐줘" / "시뮬레이션" | 기획 모드로 PHASE 1 → 2 → 3 → 4, 가정치 워터마크 |
| "발행가·수익률만 계산" | 파라미터 시트(common-core §2.6)만 산출 |
| "신고서 초안 써줘" | PHASE 1 → 2 → 3 → 4 |
| "이 초안 검토해줘" (초안 제공됨) | 초안에서 유형을 역판정 후 PHASE 4만. 유형이 불명확하면 PHASE 1 수행 |
| "투자위험요소만" / "이해상충 부분만" | 해당 절만. 단 유형은 확인 |

## 산출물

**저장 위치**: 프로젝트별 폴더 `gen-docs/st_prospectus/<slug>/` 에 모은다(loose로 흩지 않는다).

`<slug>` — **발행사+증권명 기반 kebab-case ASCII**(한글은 로마자/음역). 한 번 정하면 고정한다.
이 슬러그는 **dApp 브리지(filing-to-dapp)가 그대로 재사용**해 `gen-apps/<slug>/`로 잇는다.
예: 그린리츠 판교오피스1호 → `greenreit-pangyo-office-1`. (스킬 소스 폴더명 `sto-filing`은 슬러그로 쓰지 않는다.)

파일명 규칙:

```
gen-docs/st_prospectus/<slug>/
├── 증권신고서_<발행사>_<증권명>_초안_YYYYMMDD.md
├── 심사검토서_<발행사>_<증권명>_YYYYMMDD.md
├── 증권유형판정서_<발행사>_YYYYMMDD.md   (판정만 수행한 경우)
├── 입력요청서_<발행사>_YYYYMMDD.md        (입력요청만 수행한 경우)
└── 발행파라미터_<발행사>_YYYYMMDD.csv     (정량 파라미터 시트; 엑셀에서 열림)
```

기획 모드 산출물은 파일명 끝에 `_시뮬`을 붙인다(예: `증권신고서_..._초안_시뮬_YYYYMMDD.md`).

작성 결과를 요약할 때는 **치명·중대 지적사항 개수와 그 내용을 먼저** 말한다.
"초안을 작성했습니다"로 시작하면 사용자가 심사 결과를 놓친다.

## 이 스킬이 지켜야 할 것

**추측 금지.** 입력에 없는 사실을 채우지 않는다. 특히 기초자산 평가액, 매입가,
계약상대방, 지정번호, 재무수치. 없으면 `[미확정]`이다.
확장은 사실(F)의 함의를 서술(N)·판단(J)으로 전개하는 것이며, 없는 사실을 만드는 것이
아니다. J로 제안한 초안에는 반드시 `[발행사 확인 요망]`을 붙인다(common-core.md §1의 F/N/J).

**보장성 표현 금지.** "수익 보장", "원금 손실 없음", "안정적 수익", "확실한".
정기 분배 구조에서는 "안정적 현금흐름"류 표현이 특히 위험하다.

**불리한 사실 우선.** 위험을 먼저, 완화 요인을 나중에. 순서가 뒤집히면 그 자체가 지적 대상이다.

**법률자문이 아니다.** 모든 산출물 말미에 아래를 붙인다.

> 본 문서는 참고용 초안이며 법률자문이 아니다. 증권성 판단과 기재 적정성은
> 감독당국의 최종 해석에 따른다. 실제 제출 전 법률의견서 확보와
> 금융감독원 사전협의를 권고한다.

**규범이 움직이고 있다.** 2026년 중 토큰증권 하위법규와 조각투자 발행 모범규준이
발표될 예정이고, 기초자산 적격성 기준과 풀링 허용 범위가 여기서 확정된다.
`references/sources.md`의 1차 자료를 확인해 최신 상태를 반영한다.
확인하지 않았다면 그 사실을 사용자에게 알린다.

**근거 조문은 로컬 코퍼스를 먼저 본다 — 단, 선택 단계다.** 이 레포에 `data-platform/`이 있고
색인이 채워져 있으면(`data-platform/data/serving/index.sqlite`가 비어 있지 않음), 증권성 판단과
유통·전매제한의 근거 조문을 코퍼스에서 조회하고 `rel_path`를 인용한다. 코퍼스에는 통과된
토큰증권 개정법 2건(자본시장법·전자증권법 대안 원문)이 색인돼 있다.

```
make -C data-platform query Q="투자계약증권 장외거래 전매"      # 컬렉션 목록: make -C data-platform collections
```

data-platform이 없거나(zip 단독 배포 환경) 색인이 비어 있으면 **이 단계를 건너뛰고**
sources.md 웹 링크로 확인한다 — 스킬은 코퍼스 없이도 동일하게 완주된다. 색인 재구축
(`make build`)은 전체 파이프라인이라 무겁다 — 임의로 돌리지 말고 사용자에게 확인한다.
서식(기업공시서식 작성기준)과 정정요구 사례집은 코퍼스에 **없다** — 그건 항상 sources.md.
