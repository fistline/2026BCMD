> "상품이 여러 개인데, 하나의 컨트랙트로 묶어 관리할까요, 상품마다 컨트랙트를 따로 배포할까요?"

> 1. 상품마다 신탁·SPC 등 발행 주체가 다른가 (청약 자금을 섞으면 안 되는가)

> `DECISION.md`에 적는다 — "단순해서 D1"과 다른 말이고, 나중에 구조를 바꿔야 할 때 근거가 된다.
> 축2가 "단일"이면 이 질문은 성립하지 않는다. "해당 없음"으로 채우고 넘어간다.

## 🎯 3) Role & Output Goal

> [!IMPORTANT]
> **설계 순서와 구현 순서는 반대다. 이 둘을 혼동하지 마라.**
> - **설계(요구 도출)는 위에서 아래로**: 사용자 여정 → 필요한 데이터 → 온체인이어야만 하는 것 → 컨트랙트 표면
> - **구현(코드 생성)은 아래에서 위로**: 컨트랙트 → 테스트 → 배포 → 데이터 계층 → API → 프론트
>
> 설계를 컨트랙트에서 시작하면 여정을 지원하지 못하는 관리자 도구가 나온다.
> 구현을 프론트에서 시작하면 `deployedContracts.ts`가 없어 타입이 성립하지 않는다.

### PHASE 0 — 설계 (코드를 쓰지 않는다)

위에서 아래로 도출한다. 산출물은 **문서뿐이다.**

1. **Journey** — §1의 사용자 여정을 단계로 분해한다.
2. **Data** — 각 단계가 읽고 쓰는 데이터를 나열한다.
3. **Boundary** — §4.3 기준으로 각 데이터를 온체인 / SQLite로 배정한다.
4. **Surface** — 온체인 배정분에서 **필요한 컨트랙트 함수·이벤트만** 역산한다.
   여정이 요구하지 않는 함수는 만들지 않는다.
5. **Standard** — §5로 표준(축1·축2)과 **발행 단위(축3 D1/D2)** 를 판정한다.
   **축3은 §1 Q7의 답으로만 정한다** — 비어 있으면 추측하지 말고 묻는다.
6. **Operations** — §5.5로 운영 모델(M0~M3)과 역할 배정을 판정한다. 표준이 정해지면
   권한 함수는 이미 존재하므로, 여기서 주체를 정하지 않으면 배포자에게 전부 쏠린다.

**게이트 0**: `DECISION.md` 에 여정→화면 매핑표, 온체인/SQLite 분담표, 확정된 컨트랙트 표면(함수·이벤트 목록), 표준 판정 근거(**축1·축2·축3**), **운영 모델 판정과 역할→계정 배정표**를 기록한다. 이 문서 없이 PHASE 1로 넘어가지 않는다.

### PHASE 0.5 — 스캐폴딩 (빈 폴더에서 시작하지 않는다)

이 프롬프트는 `packages/foundry/`·`packages/nextjs/` 경로와 `useScaffoldReadContract` 같은
SE-2 훅, `deployedContracts.ts` 자동 연결을 **전제한다.** 그 뼈대는 직접 만드는 것이 아니라
Scaffold-ETH 2에서 받는 것이다. 손으로 흉내 내면 훅과 주소 자동연결이 동작하지 않는다.

```bash
forge --version                              # 없으면 여기서 멈춘다 (아래 설명)
npx create-eth@latest <slug> -s foundry      # -s = solidity-framework
cd <slug> && yarn install
```

**`-s`(solidity-framework)이지 `-e`가 아니다.** `-e`는 확장(extension) 플래그라 `foundry`를
확장 이름으로 찾다 실패한다. 대화형으로 뜨면 Hardhat 아닌 **Foundry**를 고른다.

**`forge`가 PATH에 없으면 `create-eth`가 `FoundryValidationError`로 중단한다.** 설치돼
있어도 PATH에 없으면 같은 결과다(`~/.foundry/bin`이 흔한 위치). 먼저 `forge --version`으로
확인하고, 없으면 `foundryup`을 안내하고 **여기서 멈춘다** — 뒤 단계가 전부 Foundry에 의존한다.

받은 직후 아래를 확인하고, 어긋나면 멈추고 사용자에게 알린다.

- `packages/foundry/foundry.toml`, `packages/nextjs/` 존재
- `packages/nextjs/contracts/deployedContracts.ts` 존재 (배포 전이라 비어 있는 게 정상)
- `yarn foundry:test` 가 템플릿 기본 테스트로 통과 (루트 `yarn test`도 같은 것을 가리킨다)

**게이트 0.5**: 템플릿이 그대로 기동된다. 여기서부터 템플릿 예제(`YourContract` 등)를
지우고 PHASE 0에서 확정한 표면으로 대체한다.

### PHASE 1 — 컨트랙트

PHASE 0에서 확정한 표면만 구현한다. 모듈은 §6.1, 표준 스펙은 §7 원문 참조.

**게이트 1**: `forge build` 성공 + `forge test` 전량 통과 (정상 경로 + 실패 경로). 실패 시 여기서 고치고 재실행한다. **통과 전에 PHASE 2로 넘어가지 않는다.**

### PHASE 2 — 배포 · 시드

배포 스크립트(의존 순서 단일 파일) + 로컬 시드 데이터 스크립트.

**게이트 2**: 로컬 체인에 배포 성공 + `deployedContracts.ts` 생성 확인 + `cast call` 로 대표 read 함수 1개 응답 확인.

### PHASE 3 — 데이터 계층

마이그레이션 → DB 모듈 → 인덱서 → Route Handlers. 게이트 2의 실제 ABI·주소를 사용한다.

**게이트 3**: 마이그레이션 성공 + 인덱서가 배포 블록부터 동기화 완료 + 시드 이벤트가 `indexed_events`에 적재됨.

### PHASE 4 — 프론트엔드

게이트 2의 타입과 게이트 3의 API만 사용한다. **존재하지 않는 함수·엔드포인트를 가정하지 않는다.**

**게이트 4**: `yarn dev` 단일 명령으로 전체 스택이 기동되고 브라우저에서 §1 여정이 완주된다.

### PHASE 5 — 검수

## 🧱 4) Absolute Rules (Non-Negotiable)

### 4.1 서비스 우선 원칙 (최우선 규칙)

- 화면 구성을 **컨트랙트 함수 목록에서 유도하지 않는다.** §1의 사용자 여정에서 유도한다.
- `mint` / `burn` / `setRole` 같은 함수명이 그대로 버튼 라벨이 되면 실패한 설계다. 사용자의 언어로 표현한다.
- 운영자 백오피스는 **부차 화면**이다. 첫 화면이 관리자 콘솔이면 실패한 설계다.
- 사용자가 지갑 연결 이전에도 **서비스가 무엇인지 이해하고 자산을 탐색할 수 있어야 한다.**

### 4.2 No placeholders for core features

`TODO`, `FIXME`, "생략", `...` 를 아래에 남기지 않는다:
컨트랙트 구현 / 배포 스크립트 / Foundry 테스트 / 프론트 화면 / DB 스키마·마이그레이션 / 인덱서 / 환경 설정

### 4.3 온체인 / 오프체인 경계 (엄수)

| | 온체인 | SQLite |
|---|---|---|
| 소유권·잔고·이전 권한 | ✅ 진실의 원천 | ❌ 캐시만 |
| 정산·분배 결과 | ✅ | ❌ 캐시만 |
| 자산 카탈로그 메타·설명·이미지 | ❌ | ✅ |
| 신청·심사 진행 상태 | ❌ | ✅ |
| 검색·필터·정렬·알림·감사로그 | ❌ | ✅ |

**SQLite는 언제나 재구축 가능해야 한다.** DB를 삭제하고 이벤트를 리플레이하면 동일 상태로 복원되어야 한다.
복원 불가능한 데이터를 SQLite에만 두지 않는다.

### 4.4 No missing helpers

참조한 모든 라이브러리·유틸리티는 import 경로가 해석되어야 하고, 직접 작성한 것은 전문을 함께 출력한다.

### 4.5 No unnecessary questions

명백한 요구사항에 되묻지 않는다. 수익 분배가 언급되면 분배 컨트랙트와 수령 화면을 **구현한다.**
질문은 §2의 4개 필드가 누락·모순일 때만 허용된다.

**§1 Q6·Q7이 비어 있을 때도 허용된다** — 이 둘은 서비스 서술에서 역산되지 않으므로
"명백한 요구사항"에 해당하지 않는다. 문안은 §1의 각 질문 아래에 있다.
그 외에는 되묻지 않는다. 특히 화면 구성·스키마·컨트랙트 분할은 **추론 대상이지 질문 대상이 아니다.**

### 4.6 Security & privacy

- 개인키·니모닉을 코드나 로그에 **절대 남기지 않는다.** `.env.example`만 제공한다.
- 개인식별정보(실명·연락처·신분증)를 온체인에 올리지 않는다. 온체인에는 **판정 결과(bool/해시)만** 둔다.
- 권한 함수는 역할 분리 + 이벤트 로깅. 외부 호출 함수에 checks-effects-interactions 적용.
- SQLite 쿼리는 **prepared statement만** 사용한다. 문자열 결합으로 SQL을 만들지 않는다.
- 오프체인 API의 쓰기 경로는 지갑 서명 검증(SIWE 또는 EIP-712)으로 보호한다.
- **읽기 경로도 같은 기준으로 막는다.** 심사 자료(`applications`)·운영자 행위 기록(`audit_log`)·
  승인 대기열(`admin_approvals`)을 반환하는 경로는 무인증으로 열지 않는다. 쓰기만 막고 읽기를
  열어 두면, 온체인에 올리지 않으려고 SQLite로 내린 바로 그 개인정보가 API 하나로 나간다.
  **무엇을 열지는 화면이 아니라 테이블로 정한다** — 지갑 연결 없이 보이는 것은 §9.1 탐색이
  쓰는 자산 카탈로그와 공개 문서까지다.
- 역할이 필요한 경로는 **서명한 주소의 온체인 역할을 조회해 서버에서 판정한다.**
  프론트에서 탭을 숨기는 것은 접근 제어가 아니다 — 화면을 감춰도 라우트는 그대로 열려 있다.

### 4.7 Gas & scalability

- 분배·정산은 **pull 방식으로만.** 보유자를 순회하며 전송하는 push 방식은 보유자가 늘면 가스 한도로 실패한다.
- 목록·검색·집계는 온체인 열거가 아니라 **SQLite 인덱스**에서 처리한다.
- 상태변경 함수에 무한 루프 가능한 배열 순회를 두지 않는다.

### 4.8 Premium UI/UX requirement

"Hello World"로 보이면 안 된다.

- 일관된 테마·간격·타이포그래피. 다크 기반 미니멀, 수치·주소·해시는 monospace.
- 트랜잭션 3단계 상태(대기 / 전송중 / 확정)를 항상 시각화.
- **실패는 반드시 원인이 보여야 한다.** revert 사유를 사람이 읽는 문구로 변환한다.
  ("자격 검증 실패" 가 아니라 "수신 계정이 아직 승인되지 않았습니다")
- 온체인 확정 지연 구간에 낙관적 UI를 쓰되, 실패 시 명확히 롤백한다.

## 🧠 5) Standard Inference

> [!NOTE]
> 이 판정을 **가장 먼저** 수행한다. 판정 전에 어떤 코드도 작성하지 않는다.
> 고객 요구사항에 맞는 표준을 고르는 것이지, 특정 표준을 전제하지 않는다.

### 축 1 — 이전 제약이 필요한가

§1의 4번째 질문을 기준으로 판단한다.

- **불필요** → 표준 ERC-20 계열만 사용. **ERC-7943을 넣지 않는다.**
- **필요** (KYC·적격투자자·락업·관할·보유상한 중 하나라도 언급) → ERC-7943(uRWA)로 확장

> **보유상한이 제약에 포함되면 여기서 함께 말한다 — 주소가 아니라 사람 단위다.**
> `balanceOf(to) + amount <= cap` 만 검사하는 설계는 지갑을 하나 더 만드는 것으로 끝나서,
> 규제상 "1인당 한도"를 온체인에서 통제하는 시늉만 하게 된다. 표준만 묻는 요청이라도
> 이 한 줄은 답에 넣는다 — 안 넣으면 사용자가 우회 가능한 설계를 정답으로 가져간다.
> 구현(신원→주소 집합 합산, 개인정보 경계)은 §6.1.

### 축 2 — 자산의 다중성

- **단일 자산 1종** → ERC-20
- **동종 자산 다수 / 계속 추가** → ERC-6909
- **개별 고유 자산 1물1권** — **토큰 1개에 소유자가 1명**인 경우 (회원권 1구좌, 한 사람이
  통째로 보유하는 미술품 원본·부동산 1건) → ERC-721.
  **자산이 1건이라는 것만으로 여기 오면 안 된다** — 같은 미술품 1점이라도 여럿이 조각으로
  나눠 가지면 그 조각은 서로 대체가능하고, 비율 보유상한(예: 20%)도 대체가능 잔고를
  전제한다(NFT 잔고는 0 아니면 1). 그때는 **단일 대체가능 → ERC-20**이다.

### 축 3 — 발행 단위가 분리되는가 (§1 Q7)

> [!IMPORTANT]
> **이 축은 추측하지 않는다. §1 Q7의 답으로만 정한다.** 컨트랙트 구조를 되돌리는 비용이
> 가장 크고, 답은 서비스 서술에서 역산되지 않는다 — 같은 "부동산 조각투자"라도 한 신탁에
> 여러 물건을 담을 수도, 물건마다 신탁을 따로 세울 수도 있다. **Q7이 비어 있으면 묻는다.**

축2가 "자산이 여럿인가"라면, 축3은 **"그 여럿을 한 컨트랙트에 담는가"**다. 다른 질문이다.

- **`D1` 통합** — 하나의 컨트랙트가 여러 `id`를 담는다. 같은 발행사·같은 법적 구조·같은 운영 주체.
- **`D2` 분리** — 상품마다 토큰 컨트랙트를 따로 배포한다(팩토리). 아래 중 **하나라도** 해당하면 D2:
  - 상품마다 **신탁·SPC 등 발행 주체가 다르다** (청약 자금을 섞을 수 없다)
  - 상품마다 **증권신고서가 따로** 나간다
  - 상품마다 **운영 주체·권한 보유자가 다르다** (여러 발행사의 상품을 한 플랫폼에서 취급)
  - 한 상품만 **독립적으로 정지·청산**할 수 있어야 한다

**축2가 "단일"이면 축3은 성립하지 않는다**(담을 것이 하나뿐이다). 1물1권(S5/S6)은 `tokenId`가
이미 상품을 가르므로 정당한 사유 없이는 D1이다.

### 판정 결과

| | 제약 없음 | 제약 필요 |
|---|---|---|
| **단일 대체가능** | `S1` ERC-20 | `S2` ERC-20 + ERC-7943 Fungible |
| **다중 대체가능** | `S3` ERC-6909 | `S4` ERC-6909 + ERC-7943 MultiToken |
| **1물1권** | `S5` ERC-721 | `S6` ERC-721 + ERC-7943 NonFungible |

**다중 대체가능 + `D2`이면 S3/S4가 아니다.** 컨트랙트마다 담기는 자산이 하나이므로
**상품마다 S1/S2**이고, 여기에 **팩토리 + 레지스트리**가 붙는다. 표기는 `S2 × D2`처럼 함께 쓴다.

| 축2 | `D1` 통합 | `D2` 분리 |
|---|---|---|
| 단일 자산 | S1/S2 | (성립 안 함) |
| 다중 대체가능 | **S3/S4** (ERC-6909) | **상품마다 S1/S2** + 팩토리 |
| 1물1권 | **S5/S6** (`tokenId`가 곧 상품) | 드묾 — 사유가 없으면 D1 |

**`D2`를 택하면 따라오는 것** (전부 이 문서 안에 자리가 있다):

- **신규 상품 배포가 관리자 기능이 된다** — 팩토리 + `REGISTRAR_ROLE`(§9.6 상품 탭)
- 배포 주소는 `deployedContracts.ts`에 없다 → **레지스트리·배포 이벤트에서 읽는다**(§6.2·§10.5)
- **인덱서 대상이 동적이다** — 팩토리 이벤트를 구독해 새 컨트랙트를 인덱싱 목록에 추가(§8.3)
- **대사는 상품별로 돈다** — 컨트랙트마다 `totalSupply`가 따로다(§8.5)
- **오프체인 키가 달라진다** — 각 컨트랙트의 `assetId`는 §6.1에 따라 항상 `0`이므로
  `assetId` 하나로는 상품이 구분되지 않는다. 카탈로그·이벤트·동기화 상태를 모두
  **컨트랙트 주소와 함께** 잡는다(§8.2)
- 업그레이더블 프록시는 여전히 금지(§12). 팩토리는 프록시가 아니라 **새 인스턴스**를 만든다

### 부가 확장 — 요구사항에 해당할 때만 추가

| 확장 | 추가 조건 |
|---|---|
| ERC-2612 (Permit) | 가스리스 승인 / 온보딩 마찰 최소화가 언급될 때 |
| ERC-4626 (Vault) | 자금을 모아 운용하는 풀 구조일 때 (**S1/S2만**) |
| ERC-20 Votes | 보유자 의결·거버넌스가 언급될 때 |

**언급되지 않은 확장은 추가하지 않는다.** 쓰지 않을 표준을 미리 붙이지 않는다.

### 판정 우선순위

- §2에서 표준이 **명시**되면 그것이 우선한다.
- **판정이 애매하면 더 단순한 쪽을 택한다** (제약 없음 > 제약 필요, 단일 > 다중, `D1` > `D2`).
  제약을 나중에 추가하는 비용이, 불필요한 제약을 걷어내는 비용보다 낮다.
- **단, 축3은 "애매하면 D1"로 넘기기 전에 반드시 한 번 묻는다.** 축1·축2는 서비스 서술에서
  역산되지만 축3은 되지 않고, 잘못 고르면 배포 후 되돌리는 비용이 가장 크다.
  물었는데도 답이 없을 때만 D1을 채택하고 그 가정을 통지한다.

### 기록 (필수)

**PHASE E까지 가는 실행은 `DECISION.md`에**, 표준 판정만 요청받아 짧은 경로로 끝나는
실행은 **답변 본문에** 아래 블록을 그대로 싣는다. `DECISION.md`는 프로젝트 폴더 안에 있고
그 폴더는 PHASE E에서 생기므로, 짧은 경로에서는 쓸 곳이 없다 — 그렇다고 기록을 건너뛰면
사용자가 판정 근거를 확인할 방법이 사라진다.

```
standard: S1~S6 (+ D2면 "× D2" 표기)
축1 판정: (근거가 된 §1 서술)
축2 판정: (근거가 된 §1 서술)
축3 판정: D1 / D2 — 근거가 된 §1 Q7 서술. 물어서 답을 못 얻었으면 그 사실도 적는다
부가 확장: (추가한 것 + 이유 / 없으면 "없음")
operations: M0~M3                    ← §5.5
운영 판정: (근거가 된 §1 Q6 서술 + 강제 규칙 적용 여부)
역할 배정: (역할 → 보유 계정 / M1이면 "배포자 단일")
```

## 🛡️ 5.5) Operations Model Inference (운영 모델 판정)

> [!NOTE]
> §5 **직후에 이어서** 수행한다. 표준을 고르면 운영 권한은 이미 따라온다 —
> 판정을 미루면 권한이 배포자 EOA 한 곳에 조용히 모인다.

### 왜 별도 판정인가

ERC-7943은 `forcedTransfer`·`setFrozenTokens`를 **인터페이스 필수 함수**로 두고 접근 제한 방식만
구현자에게 위임한다("MUST restrict access"). 즉 §5 축1이 "제약 필요"로 판정되는 순간
**사용자 자산을 강제로 움직이는 함수가 이미 존재한다.** 그 권한을 누가 갖는지는 선택이 아니라
**반드시 답해야 하는 질문**이다. 표준 판정만 하고 여기서 멈추면 답을 안 한 것이 아니라
"배포자 한 명이 전부 갖는다"고 답한 것이 된다.

### 축 — 운영자가 무엇에 개입하는가 (§1 Q6)

| 개입 수준 | 해당 행위 |
|---|---|
| **(a) 운영 데이터** | 자산 등록·메타 갱신, 평가액 갱신, 수익 예치 |
| **(b) 자격 판정** | 자격 승인·취소, 화이트리스트 등재 |
| **(c) 보유자 자산** | 동결(freeze), 강제이전(forcedTransfer), 지갑 분실 복구 |
| **(d) 서비스 전체** | 일시정지(pause) |

### 판정 결과

| 모델 | 포함 | 권한 구조 |
|---|---|---|
| `M0` 관리자 없음 | — | 배포 후 특권 함수 없음 |
| `M1` 단일 운영자 | (a) | 배포자 1계정이 전 역할. 로컬 시연 기본 |
| `M2` 직무 분리 | (a)+(b) | 역할별 계정 분리 + `Ownable2Step` + 감사로그 |
| `M3` 규제형 | (a)+(b)+(c)+(d) | M2 + 강제집행 역할 분리 + 2인 승인 + 총량 대사 |

> **M0은 드물다.** 시드 이후 자산이 추가되지도, 평가액이 갱신되지도, 수익이 예치되지도 않는
> **완전 고정** 구성에서만 성립한다. 평가·분배·상장 중 하나라도 계속된다면 그것을 수행할 주체가
> 있다는 뜻이므로 **M1 이상**이다. "관리자를 원하지 않는다"는 답이 곧 M0은 아니다.

### 강제 규칙 (Q6 답변보다 우선한다)

- **§5 축1 = "제약 필요"(ERC-7943) → 최소 `M2`.** (b)를 수행할 주체가 없으면 화이트리스트가
  아무도 채우지 않는 빈 목록으로 남아 서비스가 성립하지 않는다. Q6이 "없음"이어도 이 규칙이
  이기며, **그 사실을 사용자에게 통지한다.**
- **(c)를 하나라도 채택 → `M3`.** 강제이전·동결은 자격 승인과 **다른 역할**이어야 한다.
  ERC-3643이 Owner(설정·임명)와 Agent(운영 집행)를 가르는 것과 같은 정신이되, 여기서는 한 단계
  더 나눈다 — **명부를 고치는 손과 잔고를 움직이는 손을 분리한다.**
  (T-REX는 자격 등재와 강제이전을 모두 Agent에 두므로, 이 분리는 그 표준의 재현이 아니라 확장이다.)
- **(c)가 불필요하면 함수는 구현하되 역할 보유자를 두지 않는다.** ERC-7943 준수를 위해
  `forcedTransfer`·`setFrozenTokens`는 노출하고, `ENFORCER_ROLE`을 **아무에게도 부여하지 않는다.**
  표준을 깨서 함수를 빼지 않고, 권한을 방치하지도 않는다. 단 **관리자가 나중에 스스로 부여할 수
  있다는 사실**을 `DECISION.md`에 함께 적는다 — 감춰진 권한이 아니라 명시된 선택이어야 한다.
- **애매하면 낮은 쪽.** 권한을 나중에 늘리는 비용이, 잘못 준 권한을 걷어내는 비용보다 낮다
  (§5의 "단순한 쪽" 원칙과 같은 방향).

### 이번 범위의 경계

온체인 타임락·멀티시그·권한 허브(Centrifuge `Root`+Guardian의 48h/72h 지연, OpenZeppelin
`AccessManager`)는 **구현하지 않는다.** 단일 서비스·소수 컨트랙트 규모에는
`AccessControl` + `Ownable2Step`으로 충분하고, 지연·취소 계층은 운영 조직이 생긴 뒤의 문제다. 대신 `README.md`에 **승격 경로**를
문서화한다(어느 역할이 멀티시그로, 어느 함수가 타임락 뒤로 가는지). ERC-7540 승격 경로를
문서화하는 §6.3과 같은 취급이다.

`M3`의 2인 승인(4-eyes)은 **오프체인 2서명 → 온체인 1트랜잭션**으로 구현한다(§8.2·§9.6).
온체인 다중서명 컨트랙트를 만들지 않는다.

## 🔌 6) Contract Requirements

> [!WARNING]
> **표준에 이미 정의된 내용은 이 문서에 반복하지 않는다.**
> 인터페이스 시그니처, 필수 동작, ERC-165 interfaceId, 이벤트·에러 정의는 **§7의 EIP 원문을 참조해 그대로 구현한다.**
> 학습된 초안 단계 명칭을 쓰지 말고 **반드시 원문을 확인한다.**
>
> 아래에는 **이 프로젝트에 고유한 결정만** 기술한다.

### 6.1 모듈 인터페이스 (프로젝트 고유)

모든 모듈은 `assetId`를 1급 파라미터로 받는다. 단일 자산용 시그니처를 따로 만들지 않는다 —
이 규칙 덕분에 표준을 바꿔도 모듈이 재사용된다. **`assetId`에 무엇을 넣는지는 표준이 정한다.**

| 표준 | `assetId` | 왜 |
|---|---|---|
| S1 · S2 (ERC-20) | 항상 `0` | 대체가능 잔고 하나뿐이라 가를 것이 없다 |
| S3 · S4 (ERC-6909) | ERC-6909의 `id` | 그 id가 곧 자산 구분자다 |
| **S5 · S6 (ERC-721)** | **`tokenId`** | **1물1권은 토큰마다 다른 자산이다** |

**S5/S6을 `assetId = 0`으로 고정하면 안 된다.** 회원권 A와 B가 등급·만료일·가격이 달라도
`pricePerShare(0)`은 하나의 값만 돌려주고 `claimable(0, holder)`은 어느 구좌 몫인지 구분하지
못한다. 1물1권은 "자산이 하나"라는 뜻이 아니라 "**토큰 하나에 소유자가 하나**"라는 뜻이다(§5 축2).

```solidity
interface IValuation {
    function pricePerShare(uint256 assetId) external view returns (uint256);
}

interface IDistribution {
    function distribute(uint256 assetId, uint256 amount) external;
    function claimable(uint256 assetId, address holder) external view returns (uint256);
    function claim(uint256 assetId) external returns (uint256 amount);
}

interface ITransferPolicy {          // 축1 = "제약 필요" 일 때만 생성
    function canSend(address account) external view returns (bool);
    function canReceive(address account) external view returns (bool);
    function canMove(address from, address to, uint256 assetId, uint256 amount) external view returns (bool);
}
```

기본 구현체는 각 1개씩만: `ManualNAV`, `PeriodicPull`(pull 방식 필수), `WhitelistPolicy`(송신·수신 분리).
**인터페이스를 4개째 만들지 않는다.** 네 번째가 필요해 보이면 그건 대개 오프체인 계층의 문제다.

토큰 컨트랙트는 내부 `canMove(...)`를 선택한 표준의 공식 시그니처로 노출하는 **어댑터 역할**만 한다.

> **보유상한은 주소가 아니라 사람 단위로 건다.** `balanceOf(to) + amount <= cap` 만 검사하면
> 지갑을 두 개 만드는 것으로 끝난다 — 규제상 "1인당 한도"를 온체인에서 주소 한도로 구현하면
> 통제가 아니라 통제하는 시늉이다. 정책 컨트랙트가 **신원 → 보유 주소 집합**을 알고
> 그 합계로 판정해야 한다(자격 판정과 같은 자리에서 이미 신원을 다루므로 추가 계층이 아니다).
>
> 개인정보는 온체인에 올리지 않는다 — 신원은 **오프체인 식별자의 해시**로만 두고, 정책은
> `identityOf(address) → bytes32`와 그 신원의 주소 목록만 갖는다. 실명·연락처·서류는 SQLite.
> 지갑 추가·교체는 발행인 승인 경로로만 가능하게 하고 그 이벤트를 남긴다.

### 6.2 AssetRegistry — 메타데이터 최소주의

온체인에는 아래 3개 필드만 둔다:

```
assetType     bytes32
metadataURI   string
documentHash  bytes32
```

자산별 상세 속성은 **SQLite와 JSON Schema**가 담당한다(§8). 온체인 스키마를 만들지 않는다.
새 자산 유형 추가에 컨트랙트 재배포가 필요하면 설계가 잘못된 것이다.

**"새 상품을 추가한다"가 무엇을 뜻하는지는 §5 축3이 정한다. 임의로 고르지 않는다.**

- **`D1`** — 새 상품은 `registerAsset`으로 **`assetId`를 발급받는 일**이다. 컨트랙트를 배포하지
  않으며, 관리자 화면에 "컨트랙트 배포" 버튼을 만들지 않는다.
- **`D2`** — 새 상품은 **팩토리로 토큰 컨트랙트를 배포하고** 그 주소를 `AssetRegistry`에 `assetId`와
  함께 기록하는 일이다. 배포는 `REGISTRAR_ROLE`만 수행하고 이벤트를 남긴다(§9.6 상품 탭).

`D2`에서 지킬 것:

- **레지스트리는 하나로 유지한다.** 상품마다 늘어나는 것은 토큰(과 필요하면 자금 보관) 컨트랙트다.
  자산 목록·문서 해시·주소 매핑까지 흩어지면 대사도 감사도 성립하지 않는다.
- **런타임 배포 주소는 `deployedContracts.ts`에 없다.** 프론트는 레지스트리(또는 인덱싱된 배포
  이벤트)에서 주소를 읽는다 — §10.5의 "주소 하드코딩 금지"는 이 경로로 지킨다.
- 업그레이더블 프록시는 금지(§12). 팩토리는 프록시가 아니라 **새 인스턴스**를 만든다.
- 배포 가스·인덱서 대상·감사 범위가 상품 수만큼 늘어난다. **`D2`를 고른 근거를 `DECISION.md`에 적는다.**

### 6.3 자금 흐름

- **S1/S2 + 풀 구조**: ERC-4626 동기 볼트
- **그 외 (`D1`)**: `assetId`별 청약·환매 매니저 **하나**가 `assetId`로 분기. ERC-4626 미준수 사실을 컨트랙트 상단 주석에 명시
- **그 외 (`D2`)**: 상품마다 매니저 인스턴스. **자금이 상품별로 격리된다** — D2를 고른 이유가
  대개 이것이므로, 한 매니저가 여러 상품의 예치금을 들고 있으면 D2를 택한 의미가 없다

이번 범위는 **동기 정산**이다. ERC-7540 비동기(request → claim)는 구현하지 않되,
`README.md`에 승격 경로를 문서화한다(어느 함수가 `requestDeposit`/`requestRedeem`으로 분리되는지).

### 6.4 권한 표면 (§5.5 판정을 코드로)

**새 인터페이스를 만들지 않는다.** §6.1의 3개는 그대로 두고, 각 구현체의 **역할 상수와 그 부여
대상만** M 티어가 정한다. 권한은 OpenZeppelin `AccessControl`, 소유권 이전은 **`Ownable2Step`**
(1단계 `Ownable` 금지 — 주소 오타 한 번으로 컨트랙트를 영구히 잃는다).

| 역할 | 할 수 있는 것 | 사는 곳 | M1 | M2 | M3 |
|---|---|---|---|---|---|
| `DEFAULT_ADMIN_ROLE` | **역할 부여·회수만** | 전체 | 배포자 | 별도 | 별도 |
| `REGISTRAR_ROLE` | 자산 등록·메타 갱신 | AssetRegistry | 배포자 | 분리 | 분리 |
| `VALUER_ROLE` | 평가액 갱신 | ManualNAV | 배포자 | 분리 | 분리 |
| `DISTRIBUTOR_ROLE` | 수익 예치·분배 개시 | PeriodicPull | 배포자 | 분리 | 분리 |
| `COMPLIANCE_ROLE` | 자격 승인·취소 | WhitelistPolicy | 배포자 | 분리 | 분리 |
| `ENFORCER_ROLE` | 동결·강제이전·복구 | 토큰 | — | (c) 없으면 **미부여** | **COMPLIANCE와 다른 계정** |
| `PAUSER_ROLE` | 일시정지·해제 | 토큰 | — | — | 분리 |

- **관리자는 업무를 하지 않는다.** `DEFAULT_ADMIN_ROLE`에 업무 함수를 걸지 않는다. 이 계정은
  역할을 나눠주는 자리다. 자기 자신에게 업무 역할을 부여하는 것도 이벤트로 남는다.
- **권한 함수는 예외 없이 이벤트를 남긴다.** 누가·언제·무엇을·어느 자산에.
  이 이벤트와 오프체인 사유 기록(§8.2)이 대사(對査)의 두 축이다.
- **강제이전·동결은 사유 없이 실행되지 않는다.** 함수는 `bytes32 reasonHash`를 인자로 받아
  이벤트에 싣고, 사람이 읽는 사유 원문은 SQLite에 둔다(§4.6 — PII를 온체인에 올리지 않는다).
- **지갑 복구는 이전이지 재발행이 아니다.** 분실 지갑 복구는 새 주소로의 강제이전으로 구현하고,
  총량이 변하지 않아야 한다(§8.5 대사가 이것을 검증한다).
- 배포 스크립트는 **M 티어에 따라 역할을 실제로 나눠 부여한다**(§10.4).
  M2/M3인데 전 역할이 한 주소에 몰려 있으면 **게이트 2 실패**로 본다.

## 🗄️ 8) Data Layer (SQLite + better-sqlite3)

### 8.1 역할

오프체인 데이터 계층은 **서비스를 서비스답게 만드는 부분**이다. 온체인만으로는 검색·필터·신청 흐름·알림이 불가능하다.
경계는 §4.3을 엄수한다.

### 8.2 스키마 (요구사항에 따라 가감, 표는 최소 기준)

| 테이블 | 용도 |
|---|---|
| `assets` | 자산 카탈로그. 온체인 **`(컨트랙트 주소, assetId)`** ↔ 서비스 메타 매핑 + **발행 한도·운영 상태** |
| `asset_attributes` | 자산 유형별 가변 속성 (JSON Schema 검증 후 저장) |
| `asset_documents` | 문서 메타 + `documentHash` (온체인 해시와 대조) |
| `indexed_events` | 컨트랙트 이벤트 인덱스 (재구축 가능). **어느 컨트랙트에서 왔는지 함께 남긴다** |
| `sync_state` | **컨트랙트별** 마지막 처리 블록 번호 |
| `applications` | 신청·심사 진행 상태 (최종 판정 결과만 온체인 반영) |
| `notifications` | 사용자 알림 |
| `audit_log` | 운영자 행위 기록 — **실제로 쓴다.** 아래 참조 |
| `admin_approvals` | 2인 승인 대기·승인 서명 (**M3만**, §5.5) |
| `reconciliation_runs` | 총량 대사 결과 (**M3만**, §8.5) |

> **컨트랙트 주소를 키에 넣는 것은 `D2` 전용 특례가 아니다.** `D1`은 주소가 하나뿐이라
> 같은 스키마가 그대로 성립하는 **특수한 경우**일 뿐이다. 처음부터 복합 키로 잡으면
> D1 → D2 전환이 스키마 변경을 부르지 않는다.
>
> `D2`에서 이걸 빠뜨리면 이렇게 드러난다 — 상품마다 `assetId`가 §6.1에 따라 전부 `0`이라
> **카탈로그가 서로를 덮어쓰고**, `sync_state`가 단일 행이면 §8.3이 요구하는
> "새 상품은 **배포 블록부터**"를 담을 자리가 없어 나중에 상장된 상품만 거래내역이 빈다.
> `indexed_events`에 주소가 없으면 리플레이 후 어느 상품의 이벤트인지 복원되지 않는다.

**`audit_log`는 선언만 하고 비워 두지 않는다.** 관리자 경로의 **모든 쓰기**는 여기에 한 행을
남긴다: 행위자 주소, 역할, 행위 종류, 대상 자산·계정, **사람이 읽는 사유**, `reasonHash`,
트랜잭션 해시, 시각. 온체인 이벤트가 진실의 원천이고 이 표는 **왜 그랬는지**를 담는다 —
둘이 어긋나면 대사에서 잡힌다(§8.5). 스키마에만 있고 아무도 쓰지 않는 감사 로그는 없는 것만 못하다.

- 자산 검색이 필요하면 **FTS5 가상 테이블**을 구성한다.
- 마이그레이션은 번호 붙은 SQL 파일(`001_init.sql`, `002_....sql`)을 순차 적용하는 러너로 구현한다.

### 8.3 인덱서

- 컨트랙트 이벤트를 폴링해 `indexed_events`에 적재하고 `sync_state`를 갱신한다.
- **재시작 안전**: 마지막 처리 블록부터 재개하며, 중복 처리해도 결과가 같아야 한다(멱등).
- **재구축 가능**: `sync_state`를 0으로 되돌리면 전체 리플레이로 동일 상태에 도달해야 한다.
- 체인 재구성(reorg)에 대비해 확정 지연(confirmation depth)을 두고 인덱싱한다.
- **`D2`이면 인덱싱 대상이 고정 목록이 아니다.** 팩토리의 배포 이벤트를 구독해 새 상품 컨트랙트를
  대상에 추가하고, 그 컨트랙트의 **배포 블록부터** 읽기 시작한다. 대상 목록을 코드에 박아 두면
  운영 중에 상장된 상품이 통째로 인덱싱되지 않는다 — 화면에는 보이는데 거래내역만 비는 형태로
  드러나므로 발견이 늦다.

### 8.4 better-sqlite3 실행 제약 (반드시 지킬 것)

better-sqlite3는 **동기 API의 네이티브 모듈**이다. 아래를 어기면 런타임에 실패한다.

- Next.js Route Handler에서만 사용하고, 해당 파일에 **`export const runtime = "nodejs";`** 를 명시한다.
  **Edge runtime에서 동작하지 않는다.**
- 클라이언트 컴포넌트에서 import하지 않는다. DB 접근은 전부 서버 경로를 경유한다.
- 커넥션은 **싱글턴**으로 관리한다. 개발 모드 HMR로 커넥션이 중복 생성되지 않도록 `globalThis` 캐싱을 쓴다.
- 초기화 시 `db.pragma("journal_mode = WAL")`, `db.pragma("foreign_keys = ON")` 을 설정한다.
- 다중 행 삽입은 `db.transaction(...)`으로 묶는다.
- DB 파일 경로는 환경변수로 주입하고 `.gitignore`에 포함한다.

### 8.5 총량 대사 (reconciliation) — `M3`

**세 숫자가 같아야 한다.**

| 값 | 출처 | 의미 |
|---|---|---|
| `onchain_total` | 온체인 `totalSupply(assetId)` — **`D2`이면 상품 컨트랙트마다** | 진실의 원천 |
| `indexed_sum` | 인덱싱된 보유자 잔고의 합 | 오프체인 재구성 결과 |
| `catalog_cap` | `assets` 카탈로그의 발행 한도 | 발행하기로 한 양 (상장 시 `REGISTRAR`가 확정, §9.6) |

- `indexed_sum ≠ onchain_total` → **인덱서 결함**(누락·중복·리오그). 색인을 버리고 재구축한다.
- `onchain_total > catalog_cap` → **초과분**. 발행이 한도를 넘었다. 관리자 화면에 경보를 띄우고
  해소될 때까지 신규 발행 경로를 막는다.
- 인덱서 동기화 직후마다 실행하고 결과를 `reconciliation_runs`에 남긴다.
  **불일치를 조용히 넘기지 않는다.**

> [!NOTE]
> 장식이 아니라 국내 제도의 요구다. 개정 「주식·사채 등의 전자등록에 관한 법률」은
> 발행인계좌관리기관에 **초과분 해소와 전자등록 안정성 확보를 위한 재원 적립·관리 의무**를
> 지우고(제42조의2 신설), 분산원장 이용 기준 위반에는 형사처벌을 둔다(제23조의2·제73조).
> 실제 조각투자 서비스의 투자설명서도 "계좌관리기관과 거래내역을 정산하고 보유·발행 총량을
> 검증"하는 절차와 **시차·오류로 인한 일시적 권리관계 불일치 위험**을 위험요소로 적는다.
> 이 화면이 그 절차가 사는 자리다.

화면은 **사용자 여정 순서**로 구성한다. 아래는 최소 골격이며, §1에 따라 이름과 내용을 서비스 언어로 바꾼다.

### 9.1 랜딩 / 탐색 (지갑 연결 불필요)

- 서비스가 무엇인지 즉시 이해되는 첫 화면

- 자산 상세 — 메타, 문서, 현재 평가액, 참여 조건. **지갑 없이도 열람 가능**

### 9.2 온보딩

- 지갑 연결 (RainbowKit)
- 자격 제한이 있는 경우: 신청 → 심사 대기 → 승인 상태를 사용자에게 **명확히 표시**
  (온체인에는 판정 결과만, 신청 내역은 SQLite)
- 자격이 불필요한 경우: 이 단계를 만들지 않는다

### 9.3 참여

- 청약 / 구매 / 예치 — 서비스 성격에 맞는 명칭으로
- 실행 전 **사전 검증 결과를 먼저 보여준다** (자격, 한도, 잔고). 트랜잭션을 던져놓고 실패시키지 않는다
- 진행 상태 3단계 시각화 + 완료 후 보유 화면으로 자연스러운 연결

### 9.4 보유 / 수익

- 내 포트폴리오 — 보유 수량, 제약이 있는 경우 **가용 수량을 분리 표시**
- 평가액 추이 (인덱싱된 이벤트 기반)
- 수익·배당 조회 및 수령(claim)
- 거래 내역 (SQLite 인덱스)

### 9.5 이전 / 회수

- 이전(transfer) — 제약이 있는 경우 **실행 전 검증 결과와 차단 사유를 먼저 표시**
- 환매(redeem)
- 차단 시 "무엇이 부족한지"와 "어떻게 해결하는지"를 함께 안내

### 9.6 운영자 백오피스 (부차 화면 — 내용은 §5.5의 M 티어가 정한다)

**메인 내비게이션에 노출하지 않는다.** 첫 화면이 관리자 콘솔이면 실패한 설계다(§4.1).
권한 없는 지갑에는 **경로가 보이지 않고**, 직접 URL로 접근해도 열리지 않는다.

화면은 기능 목록이 아니라 **직무 단위**로 가른다 — 지금은 한 사람이 전부 하더라도 탭이
나뉘어 있어야 사람이 늘 때 권한만 옮기면 된다(실무의 명부관리·투자자심사·펀드운영 분업).

| 티어 | 탭 | 내용 |
|---|---|---|
| M1+ | **상품** | 상품 목록·현황, 신규 상장, 메타·평가액 갱신, 수익 예치 (아래 상세) |
| M2+ | **심사** | 자격 신청 큐 → 승인/반려(**사유 필수**). 온체인엔 판정 결과만 |
| M2+ | **감사** | `audit_log` 조회·필터. 행위자·역할·사유·tx 해시 |
| M2+ | **권한** | 역할 보유자 목록과 변경 이력. `DEFAULT_ADMIN_ROLE`이 누구인지 **항상 보인다** |
| M3 | **집행** | 동결·해제, 강제이전, 지갑 복구. 사유 입력 + **2인 승인 후에만** 실행 |
| M3 | **대사** | §8.5의 세 숫자와 차이, 최근 실행 이력, 불일치 경보 |
| M3 | **정지** | 일시정지·해제. 정지 중에도 **열람은 되고 쓰기만** 막힌다 |

**상품 탭 — 자산이 여럿이면(S3·S4·S5·S6) 여기가 백오피스의 중심이다.**

투자자용 카탈로그(§9.1)를 재사용하지 않는다. 그쪽은 "살 수 있는 것"만 보이고, 운영자는
**아직 못 파는 것과 이미 끝난 것까지** 봐야 한다.

1. **상품 목록** — 온체인 `assetId` ↔ 카탈로그를 조인해 한 줄에: 상품명 · `assetId` ·
   **상태**(초안/청약중/마감/운영중/청산) · 발행량/한도 · 보유자 수 · 최근 평가액과 갱신일 ·
   미분배 수익 · (M3) 대사 상태. 검색·정렬·페이지네이션은 SQLite(§4.7).
2. **신규 상장** — 온체인 1건과 오프체인 N건이 **하나의 단위**로 처리된다:
   - **`D1`**: 온체인 `registerAsset(assetType, metadataURI, documentHash)` → **`assetId` 발급**(이벤트)
   - **`D2`**: 팩토리로 **상품 컨트랙트를 배포**하고 그 주소를 `assetId`와 함께 레지스트리에 기록.
     이 화면이 **배포 버튼이 정당하게 존재하는 유일한 자리**다(§5 축3·§6.2). 배포 전에
     대상 체인·가스·배포자 계정을 확인시키고, 배포 후 **주소와 배포 블록**을 화면에 남긴다 —
     인덱서가 그 블록부터 읽어야 하기 때문이다(§8.3)
   - 오프체인 `assets`(이름·설명·이미지·**발행 한도**), `asset_attributes`(유형별 **JSON Schema 검증** 후 저장),
     `asset_documents`(파일 + keccak256, 온체인 `documentHash`와 대조)
   - 초기 평가액(`VALUER`)과 청약 조건
   - **온체인이 확정된 뒤에 오프체인을 커밋한다.** 순서가 반대면 체인에 없는 상품이 목록에 뜬다.
   - **재시도가 같은 상품을 두 번 만들지 않아야 한다.** 멱등 키를 둔다(`documentHash` 또는 외부 상품코드).
3. **발행 한도(`catalog_cap`)는 상장 시 `REGISTRAR`가 확정한다.** §8.5 대사의 기준선이 여기서 정해지므로
   비워 둘 수 없다. 이후 변경은 **사유와 함께 `audit_log`** 에 남긴다 — 초과분이 나왔을 때
   한도를 올려 덮는 일이 조용히 일어나서는 안 된다.
4. **문서 해시 대조 배지** — 오프체인 파일 해시 ≠ 온체인 `documentHash`면 "정정 필요"로 표시한다.
5. **상장 중단은 삭제가 아니다.** 목록에서 내려도 기존 보유자의 조회·수익 수령·이전은 계속 되어야 한다.

**배포 버튼의 유무는 §5 축3이 정한다.** `D1`이면 만들지 않는다(상품 추가 = `assetId` 발급).
`D2`이면 여기에 두고, 배포 주소는 레지스트리에서 읽는다(`deployedContracts.ts` 가정 금지, §10.5).

**M3 집행 탭의 2인 승인**은 온체인 멀티시그가 아니라 오프체인 2서명이다:

```
1. 신청자(ENFORCER)가 대상·수량·사유 입력 → EIP-712 서명 → admin_approvals 에 pending
2. 승인자(다른 역할 보유자)가 같은 payload 에 서명 → 두 번째 서명 저장
3. 서명 2개가 모인 뒤에야 온체인 1 트랜잭션 실행 → tx 해시를 audit_log 에 결속
```

- **신청자와 승인자가 같은 주소면 거부한다.** 이 검사가 없으면 4-eyes가 아니다.
- payload에 대상·수량·사유해시·nonce·만료를 넣어 **재사용을 막는다.**
- 승인 대기 중에는 사용자 화면에 아무 변화가 없어야 한다 — 실행 전에는 아무 일도 일어나지 않는다.

**보유자 관점의 투명성**: 동결·강제이전을 당한 계정은 자기 포트폴리오에서 **그 사실과 사유,
문의 경로**를 볼 수 있어야 한다. 잔고가 설명 없이 줄어 있는 화면을 만들지 않는다.

### 9.7 Diagnostics

배포 주소·연결 상태, 인덱서 동기화 상태(마지막 블록·지연), 최근 트랜잭션 로그(가스·revert 원문),
임의 파라미터에 대한 이전 가능 여부 드라이런.

### 10.2 단일 명령 실행 (필수 산출물)

> [!IMPORTANT]
> **최종 목표는 `yarn dev` 한 번으로 전체 스택이 기동되는 것이다.**
> 사용자가 4개 터미널을 순서 맞춰 여는 방식은 실패로 간주한다.

루트 `package.json`에 아래를 **직접 구현해 출력한다.**

```jsonc
{
  "scripts": {
    "dev": "...",          // 원커맨드. 아래 순서를 보장할 것
    "dev:reset": "...",    // 체인 데이터 + SQLite 삭제 후 dev
    "chain": "...",        // anvil
    "deploy": "...",       // 컨트랙트 배포 + deployedContracts.ts 생성
    "db:migrate": "...",   // SQLite 마이그레이션
    "db:seed": "...",      // 로컬 시연용 시드
    "indexer": "...",      // 이벤트 인덱서
    "test": "..."          // forge test
  }
}
```

`yarn dev` 가 보장해야 할 순서:

```
1. anvil 기동
2. RPC 응답 대기          ← 반드시 대기. sleep 고정값이 아니라 준비 확인
3. 컨트랙트 배포 + deployedContracts.ts 생성
4. SQLite 마이그레이션 + 시드
5. 인덱서 · Next.js dev 서버 병렬 기동
6. 준비 완료 후 접속 URL 출력
```

- 오케스트레이션은 `concurrently` + `wait-on` (또는 동등한 방식)으로 구현하고 **의존 패키지를 `package.json`에 추가**한다.
- **멱등해야 한다.** 재실행해도 깨지지 않는다(마이그레이션은 이미 적용분 skip, 시드는 upsert).
- `npm run dev` 로도 동작해야 한다.
- 종료 시 하위 프로세스를 모두 정리한다(고아 anvil 금지).
- 각 단계 진행 상황을 콘솔에 명확히 출력한다. 조용히 멈춰 있는 구간을 만들지 않는다.

### 10.4 컨트랙트

Solidity `^0.8.24` / Foundry / OpenZeppelin(`AccessControl`, `Ownable2Step`, `ReentrancyGuard` 등 필요한 것만).

**M2/M3는 역할을 실제로 나눠 배포한다.** anvil 기본 계정을 직무별로 배정하고 — `#0` 배포·
`DEFAULT_ADMIN`, `#1` REGISTRAR·VALUER, `#2` COMPLIANCE, `#3` DISTRIBUTOR, `#4` ENFORCER,
`#5` PAUSER (티어에 없는 역할은 **부여하지 않는다**) — 어느 계정이 무엇을 갖는지 배포 로그와
`README.md`에 출력한다. 전 역할이 한 주소에 몰린 채로 M2/M3를 보고하지 않는다.

테스트는 정상 경로와 **실패 경로를 각각** 검증한다. 제약이 있는 경우 차단 케이스 테스트가 반드시
존재해야 한다. **M1보다 높은 티어면 아래를 추가로 포함한다:**

- 권한 없는 계정이 각 권한 함수를 호출하면 revert 한다 (역할마다 1건)
- **M3**: `COMPLIANCE` 계정이 `forcedTransfer`를 호출하면 revert 한다 (직무 분리가 실제로 걸렸는지)
- **M3**: 강제이전·지갑복구 전후로 `totalSupply`가 변하지 않는다
- (c) 미채택이면 `ENFORCER_ROLE` 보유자가 **0명**임을 확인한다

### 10.5 프론트엔드 / 서버

### 10.6 알려진 실행 함정 (실측)

아래는 이 프롬프트로 실제 dApp을 만들다 **기동을 막았던** 것들이다. 추측이 아니라 겪은 것이므로
같은 자리에서 다시 멈추지 않도록 미리 처리한다. 다만 환경이 바뀌면 사실도 바뀐다 —
**증상이 안 나타나면 우회를 넣지 않는다.**

| 증상 | 원인 | 처리 |
|---|---|---|
| `yarn install` 이 `better-sqlite3` node-gyp 에서 실패 | 템플릿이 끌어오는 구버전에 현재 Node 용 prebuilt 가 없어 소스 빌드로 떨어진다 | `better-sqlite3` 를 **prebuilt 가 있는 최신 메이저**로 올린다. 설치 후 `node -e "require('better-sqlite3')"` 로 확인 |
| 프론트 번들이 미배포 패키지(`@x402/*` 등) 를 못 찾아 빌드 실패 | RainbowKit 의 지갑 목록이 딸려오는 SDK 를 타고 들어간다 | 로컬 데모는 지갑 목록이 필요 없다 — `@wagmi/core` 의 `injected()` 커넥터만 쓰고, 해결 불가한 선택적 의존은 `webpack.IgnorePlugin` 으로 제외한다 |
| `yarn dev` 가 수 분씩 걸린다 | anvil 에 `--block-time` 을 주면 배포 트랜잭션마다 블록을 기다린다 | 로컬 체인은 **즉시 채굴**로 띄운다(`--block-time` 없이). 로컬은 재구성이 없으므로 인덱서 확정 지연도 0 으로 둔다 |
| 체인을 다시 띄웠는데 인덱서가 멈춘다 | 새 체인의 블록 높이가 저장된 `last_block` 보다 낮다 | 인덱서 기동 시 **헤드 높이와 배포 주소 지문**을 비교해, 되감겼거나 재배포됐으면 색인을 비우고 배포 블록부터 다시 읽는다 |

버전을 이 문서에 못 박지 않는 이유 — 숫자를 적으면 그 숫자가 낡는다. **확인 방법**을 적었으니
설치 후 실제로 확인하고, 막히면 그 사실과 조치를 `ASSUMPTIONS.md` 에 남긴다.
