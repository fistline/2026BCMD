# 항목별 확장 루브릭 (PHASE C)

사용자의 축약된 답을 **프롬프트가 그대로 소비할 수 있는 완결된 서술**로 확장한다.
각 항목마다: 무엇을 결정하는가 → 약한 답 → 강한 답이 담아야 할 것 → 짧은 예시.

> 확장의 목표는 분량이 아니라 **하류 결정을 명확히 유도하는 것**이다. 표준(§5), 화면(§9),
> 컨트랙트 표면(§6)이 여기서 역산된다. 특히 Q3·Q4는 표준을 가르므로 애매하게 두지 않는다.

---

## Q1 — 한 문장 정의 (누가, 무엇을 하러 오는가)

**결정하는 것**: 서비스의 정체성. 첫 화면 카피와 전체 톤.

- 약한 답: "부동산 토큰" (누가·무엇을·왜가 없음)
- 강한 답에 담을 것: **대상 사용자** + **그들이 달성하려는 목적** + **차별점 한 조각**. 한 문장 유지.
- 예시: "소액 투자자가 검증된 임대 부동산의 지분을 사고, 매월 임대수익을 자동 정산받는 조각투자 서비스."

## Q2 — 핵심 사용자 여정 (처음 방문 → 목적 달성)

**결정하는 것**: 화면 구성과 순서(§9), 낙관적 UI가 필요한 지점.

- 약한 답: "가입하고 산다"
- 강한 답에 담을 것: **순서 있는 단계**로, 사용자의 언어로. 최소 라이프사이클을 관통 —
  1) 지갑 없이 탐색/이해 → 2) 온보딩(지갑 연결, 필요 시 자격 신청·심사) → 3) 참여(청약/구매/예치) →
  4) 보유·수익(포트폴리오·평가액·수익 수령) → 5) 이전/회수(전송·환매, 제약 시 사유 표시).
- 각 단계에서 **사용자가 보는 것/하는 것**을 명시. 실패·차단 지점의 안내 문구 방향도 한 줄씩.
- 예시: "① 연결 없이 자산 목록·수익률·문서 열람 → ② 지갑 연결 후 KYC 신청, 승인 대기 상태 표시 →
  ③ 원하는 물건에 USDC로 청약, 사전 검증(자격·한도·잔고) 결과를 먼저 보여줌 →
  ④ 내 포트폴리오에서 보유 지분·월 임대수익 확인 및 수령(claim) →
  ⑤ 승인된 상대에게만 지분 이전, 차단 시 사유·해결법 안내."

## Q3 — 자산과 가치·수익 (축2에 직결)

**결정하는 것**: 자산 다중성(축2) → S1/S2 vs S3/S4 vs S5/S6. 자금 흐름(§6.3)과 분배 화면(§9.4).

- 약한 답: "부동산"
- 강한 답에 담을 것:
  - **자산 클래스와 다중성**: 단일 1종인가 / 동종 다수·계속 추가인가 / 개별 고유 1물1권인가.
    (이게 축2 판정 근거가 된다. "여러 물건을 계속 상장" = ERC-6909, "미술품 원본 1점" = ERC-721.)
  - **가치·수익 경로**: 임대수익/시세차익/배당/이자/로열티/환매 중 무엇이, 언제, 어떻게 사용자에게 오는가.
    정기 분배가 있으면 **pull 방식 claim**으로 구현된다(§4.7).
  - **정산 자산**: MockUSDC(6 decimals) 고정.
  - 풀에 자금을 모아 운용하는 구조면 그렇게 명시(→ S1/S2 한정 ERC-4626 볼트 후보, §6.3).
- 예시: "검증된 임대 부동산을 물건별로 계속 상장(동종 다수). 각 물건 지분 보유자는 관리사가 매월
  예치하는 임대수익을 보유 비율대로 claim. 정산·수익은 MockUSDC. 청약·환매는 물건별 매니저로 처리."

## Q4 — 보유·이전 자격 제한 (축1에 직결 — 표준을 가르는 한 줄)

**결정하는 것**: 이전 제약 필요 여부(축1) → ERC-7943(uRWA) 확장 여부. 온보딩 심사 화면(§9.2)과
이전 차단 UX(§9.5)의 존재.

- 약한 답: 비워둠 / "잘 모르겠음"
- 강한 답에 담을 것: 아래 중 **해당하는 것을 구체적으로**, 없으면 명시적으로 **"없음"**.
  - KYC/AML 통과 요건 · 적격투자자 한정 · 락업 기간 · 관할(거주지) 제한 · 1인 보유상한 · 화이트리스트 전송
  - 온체인에는 **판정 결과(bool/해시)만**, 실명·신분 자료는 SQLite(§4.6, §4.3).
- **판정 규칙**: 위 중 하나라도 언급 → 축1 "제약 필요" → ERC-7943. 전부 아니면 "없음" → 표준 ERC-20 계열,
  **ERC-7943을 넣지 않는다.** 애매하면 §5 우선순위에 따라 **제약 없음**을 택하고 그 가정을 통지한다.
- 예시(제약 필요): "KYC를 통과한 계정만 보유·수신 가능. 승인은 운영자가 온체인에 판정 결과만 기록.
  관할·적격투자자 제한은 이번 범위 없음. 락업 없음."
- 예시(제약 없음): "없음 — 누구나 자유롭게 보유·이전. (→ 표준 ERC-20/6909 계열, ERC-7943 미적용)"

## Q5 — 화면 동작·표현

**결정하는 것**: UI 상태·상호작용 세부(§4.8 프리미엄 UI, §9 화면).

- 약한 답: "예쁘게"
- 강한 답에 담을 것:
  - **지갑 미연결 방문자가 보는 것**: 서비스 이해 + 자산 탐색이 연결 없이 가능해야 함(§4.1).
  - **핵심 화면**: 랜딩/카탈로그(검색·필터·정렬) → 자산 상세(메타·문서·평가액·참여조건) →
    참여 폼(사전 검증 먼저) → 포트폴리오(가용/제약 수량 분리) → 수익 수령 → 이전/환매.
  - **트랜잭션 상태 3단계**(대기/전송중/확정) 시각화, 실패 시 **사람이 읽는 revert 사유**.
  - 톤: 다크 기반 미니멀, 수치·주소·해시는 monospace. 낙관적 UI + 실패 롤백.
  - 운영자 백오피스는 **부차 화면**, 메인 내비 비노출.
- 예시: "다크 미니멀. 랜딩은 상품 카드 그리드(수익률·잔여지분 배지). 상세는 좌측 문서/우측 청약 패널.
  청약 전 자격·한도·잔고 프리체크 배너. 포트폴리오는 보유·가용 수량과 누적 수익을 카드로.
  이전 화면은 수신자 입력 즉시 canReceive 드라이런 결과 표시. 모든 tx는 3단계 토스트, 실패 시 원인 문구."

## 확장 후 자체 점검 (PHASE D 직전)

- [ ] Q4에서 이전 제약(축1)이 "필요/없음"으로 명확한가? → ERC-7943 포함 여부 확정 가능
- [ ] 부가 확장(2612/4626/Votes)은 **언급된 근거가 있을 때만** 붙였는가? (가스리스/풀운용/거버넌스)
- [ ] 애매한 곳은 더 단순한 표준을 택하고 그 가정을 통지문에 남겼는가?
- [ ] 서술에 컨트랙트 함수명이 아니라 서비스 언어를 썼는가?
- [ ] 지어낸 고유명·수치가 없는가? (모두 "로컬 시드" 자리표시로)
