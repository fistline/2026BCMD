# 발행 단위 (Q7 → D1 / D2)

**판정 규범의 정본은 프롬프트 §5 축3이고, 구현 규칙은 §6.2·§6.3·§8.3·§9.6이다.**
여기는 스킬 쪽 일만 담는다 — **어떻게 묻고, 답을 어떻게 확장하고, 왜 물어야만 하는가.**

---

## 0. 왜 이것만은 추론하지 않는가

축1(제약)과 축2(다중성)는 서비스 서술에서 역산된다. **축3은 안 된다.**
같은 "임대 부동산 조각투자"라도 —

- 한 신탁에 여러 물건을 담고 물건별 지분을 발행 → **D1** (한 컨트랙트, 여러 `id`)
- 물건마다 신탁을 세우고 각각 증권신고서를 내고 각각 청약 → **D2** (상품마다 컨트랙트)

둘 다 현실에 존재하고, 서비스 설명만으로는 어느 쪽인지 알 수 없다. 그런데 이 선택은
**컨트랙트 구조·인덱서 대상·관리자 화면·자금 격리를 동시에** 가르고, 배포한 뒤에는 되돌릴 수 없다.
그래서 이 스킬은 **묻는다.** "단순한 쪽" 원칙으로 조용히 D1을 채택하지 않는다.

> 축2가 **단일**이면 이 질문은 성립하지 않는다 — Q7을 "해당 없음"으로 채우고 넘어간다.

---

## 1. 질의 (PHASE B, 축2=다중일 때만)

서비스·운영 질문과 **같은 왕복**에 세 번째 질문으로 붙인다.

- **question**: "상품이 여러 개인데, 하나의 컨트랙트로 묶어 관리할까요, 상품마다 컨트랙트를 따로 배포할까요?"
- **header**: "발행 단위"
- **options (3개)**

| label | description |
|---|---|
| **하나로 묶는다** | 한 컨트랙트가 상품마다 `id`를 갖는다. 상품 추가는 등록 한 번, 가스·운영이 가볍다. 같은 발행사·같은 신탁 구조일 때 (→ D1) |
| **상품마다 따로 배포한다** | 상품마다 신탁·SPC가 다르거나, 증권신고서가 따로 나가거나, 상품별로 운영 주체·정지 범위가 달라야 할 때. 관리자 화면에 배포 기능이 생긴다 (→ D2) |
| **잘 모르겠음** | 아래 판단 힌트로 되짚어 준다 |

### "잘 모르겠음"일 때 되짚는 4가지

하나라도 "예"면 **D2**다. 전부 "아니오"면 D1이다.

1. 상품마다 **신탁·SPC 등 발행 주체가 다른가?** (청약 자금을 섞으면 안 되는가)
2. 상품마다 **증권신고서가 따로** 나가는가?
3. 상품마다 **운영 주체·권한 보유자가 다른가?** (여러 발행사의 상품을 한 플랫폼에서 취급)
4. 한 상품만 **독립적으로 정지·청산**할 수 있어야 하는가?

되짚은 뒤에도 답이 없으면 **D1을 채택하되, "물었으나 정해지지 않아 D1로 갑니다"를 명시**한다.
"단순해서 D1"과 "못 정해서 D1"은 다른 말이고, 나중에 구조를 바꿔야 할 때 근거가 된다.

## 2. Q7 확장 루브릭 (PHASE C)

**결정하는 것**: 축3 판정(§5), 상품 추가의 의미(§6.2), 자금 격리(§6.3),
인덱서 대상의 동적 여부(§8.3), 관리자 상품 탭의 배포 기능(§9.6).

- 약한 답: "여러 개예요" (축2 답과 구분이 안 된다 — 이건 Q3의 답이다)
- 강한 답에 담을 것:
  - **D1인가 D2인가**, 그리고 **왜** — 위 4가지 중 어디에 해당하는지
  - D2라면: 상품마다 무엇이 배포되는가(토큰만인가, 청약·환매 매니저까지인가)
  - D2라면: **누가 배포 권한을 갖는가** (Q6의 역할 배정과 이어진다 — 보통 `REGISTRAR`)
- **사용자 답을 확장하되 뒤집지 않는다.** 축1·축2는 애매하면 전문가 판단으로 단순한 쪽을
  택하지만, 축3에서 그러면 **사용자가 모르는 사이에 컨트랙트 구조가 바뀐다.**

### 예시

**D1** — "임대 물건을 하나의 신탁에 담아 물건별 지분을 발행한다. 발행사와 수탁자가 모든 물건에
동일하고 증권신고서도 묶어서 낸다. 새 물건은 자산 등록으로 추가되며 컨트랙트는 하나를 유지한다."

**D2** — "물건마다 별도 신탁을 세우고 각각 증권신고서를 낸다. 물건 A의 청약 자금이 물건 B로
섞이면 안 되므로 토큰과 청약·환매 매니저를 상품마다 배포한다. 배포 권한은 자산 담당(REGISTRAR)이
가지며, 배포 주소는 레지스트리에 기록돼 화면이 거기서 읽는다. 한 물건에 사고가 나면
그 물건만 정지할 수 있어야 한다."

## 3. D2를 택하면 따라오는 것 (요약 — 정본은 프롬프트)

| 영역 | D1 | D2 |
|---|---|---|
| 표준(§5) | S3/S4 (ERC-6909) | **상품마다 S1/S2** + 팩토리·레지스트리 |
| 상품 추가(§6.2) | `registerAsset` → `assetId` 발급 | **팩토리 배포** + 주소를 레지스트리에 기록 |
| 자금(§6.3) | 매니저 하나가 `assetId`로 분기 | **상품마다 매니저 = 자금 격리** |
| 인덱서(§8.3) | 고정 대상 목록 | **팩토리 이벤트 구독 → 동적 추가**, 배포 블록부터 |
| 대사(§8.5) | `assetId`별 | **컨트랙트별** `totalSupply` |
| 주소 해석(§10.5) | `deployedContracts.ts` | 고정분만 자동연결, **상품분은 레지스트리 조회** |
| 관리자 화면(§9.6) | 배포 버튼 없음 | **배포 버튼이 정당하게 존재하는 유일한 자리** |
| 정지(M3) | 전 상품 동시 | **상품 단위 정지 가능** |

**바뀌지 않는 것**: 레지스트리는 하나다. 자산 목록·문서 해시·주소 매핑까지 흩어지면
대사도 감사도 성립하지 않는다. 그리고 프록시는 여전히 금지 — 팩토리는 새 인스턴스를 만든다.

## 4. 왜 D2가 "예외"가 아닌가 (근거 · 2026-07 확인)

**규제 증권 토큰의 업계 주류는 오히려 상품별 배포다.** ERC-3643의 `TREXFactory`는 발행 건마다
토큰 + IdentityRegistry + IdentityRegistryStorage + ClaimTopicsRegistry + TrustedIssuersRegistry +
Compliance **한 벌을 통째로** 단일 트랜잭션에 배포한다. 즉 **토큰 하나 = 증권 하나**가 전제다.
(https://docs.erc3643.org/erc-3643/smart-contracts-library/tokens-factory)

**ERC-6909은 이 선택에 답을 주지 않는다.** 스펙은 ERC-1155의 경량 대체재를 자처하며 콜백·배치를
덜어내는 데 집중하고, **언제 다중토큰 컨트랙트를 쓰고 언제 나눌지는 논하지 않는다** —
다중토큰이 이미 바람직하다고 전제한다. 그러니 "ERC-6909이니까 하나로 묶는다"는 순환논증이다.
(https://eips.ethereum.org/EIPS/eip-6909)

**국내 조각투자의 기본형도 상품별 분리에 가깝다.** 물건마다 신탁계약이 따로 있고 증권신고서가
따로 나가며, 발행인계좌관리기관의 총량 관리 단위도 종목별이다.

> 그래서 이 저장소는 D2를 예외로 두지 않는다. **묻고, 답에 맞춰 설계한다.**

## 5. 자주 틀리는 것

- **축2와 축3을 같은 질문으로 취급** — "상품이 여러 개"는 축2의 답이다. 축3은 "그 여럿을
  한 컨트랙트에 담는가"이고, 답이 다르면 컨트랙트 구조가 통째로 달라진다.
- **묻지 않고 D1로 진행** — 가장 흔하고 가장 비싸다. D1은 기본값이지 무응답의 동의어가 아니다.
- **D2인데 매니저를 하나만 둠** — 자금 격리가 D2를 택한 이유인데 예치금이 한 컨트랙트에 모이면
  택한 의미가 없다.
- **D2인데 인덱서 대상을 코드에 박음** — 운영 중 상장된 상품이 통째로 인덱싱되지 않는다.
  화면에는 뜨는데 거래내역만 비어서 발견이 늦다.
- **D2인데 상품 주소를 `deployedContracts.ts`에서 찾음** — 거기 없다. 레지스트리에서 읽는다.
- **1물1권(S5/S6)에 D2 적용** — `tokenId`가 이미 상품을 가른다. 정당한 사유 없이는 D1이다.
