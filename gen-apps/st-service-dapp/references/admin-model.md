# 운영 모델 (Q6 → M0~M3)

**판정 규범의 정본은 프롬프트 §5.5(판정)와 §6.4(역할 배정)다.** 이 파일은 그것을
반복하지 않고 스킬 쪽 일만 담는다 — **어떻게 묻고, 어떻게 확장하고, 왜 그렇게 정했는가.**

---

## 1. 질의 (PHASE B)

서비스 질문과 **같은 왕복에서** 던진다. 별도 왕복으로 미루지 않는다.

- **question**: "이 서비스는 누가 운영하나요? 운영자가 사용자 자산에 어디까지 개입할 수 있어야 하는지 골라 주세요."
- **header**: "운영"
- **options (4개)**

| label | description |
|---|---|
| **운영자 없음 / 최소** | 자산 등록·평가 갱신 정도만. 누구나 자유롭게 보유·이전 (→ M1) |
| **자격 심사까지** | 위 + KYC·적격투자자 승인/취소를 운영자가 수행. 승인된 계정만 보유 (→ M2) |
| **강제 개입까지** | 위 + 동결·강제이전·지갑 분실 복구·일시정지. 규제 대응·분쟁 처리용 (→ M3) |
| **잘 모르겠음** | 서비스 성격에 맞춰 추천받는다 |

`AskUserQuestion`이 없으면 **같은 내용을 표로 답변에 싣는다**(intake.md의 원칙과 동일 —
도구 유무가 물어볼 내용을 바꾸지 않는다).

### 묻지 않아도 되는 경우

- **신고서 기반**(`filing-to-dapp`) — 전매제한·투자자 보호 요건이 이미 M3을 함의한다.
- 사용자가 이미 말했다 — "KYC 승인은 우리가 한다"(→ b), "분실 지갑 복구가 필요하다"(→ c).
- **"잘 모르겠음" 또는 무응답** — 되묻지 말고 강제 규칙대로 정하고 통지한다:
  축1 제약 필요 → **M2**, 제약 없음 → **M1**.

## 2. Q6 확장 루브릭 (PHASE C)

**결정하는 것**: 운영 모델(§5.5), 역할 상수와 부여 대상(§6.4), 백오피스 탭 구성(§9.6),
감사·대사 테이블의 존재(§8.2·§8.5).

- 약한 답: "관리자 페이지 만들어줘" (누가·무엇에 개입하는지가 없다)
- 강한 답에 담을 것:
  - **운영 주체가 누구인가** — 발행사 1인 / 발행사+수탁 분업 / 별도 심사 담당
  - **(a)~(d) 중 어디까지** 개입하는가. 특히 **(c) 보유자 자산 개입 여부를 명시**한다
  - **상품이 계속 늘어나는가**(축2 다중) — 그렇다면 (a)의 중심은 "메타 갱신"이 아니라
    **신규 상장과 상품 현황 관리**다. 누가 상장을 결정하고 발행 한도를 정하는지까지 쓴다
  - **왜 필요한가** — 규제 요구인지, 분쟁 처리인지, 단순 운영 편의인지.
    이유가 없는 권한은 넣지 않는다
  - (c)를 채택하면 **누가 신청하고 누가 승인하는지**(2인 승인의 두 주체)
- 서비스 언어로 쓴다. `forcedTransfer`가 아니라 "법원 명령에 따른 강제 이전".

### 예시

**M1** — "운영자는 발행사 1인이며, 자산 정보와 평가액을 갱신하고 수익을 예치하는 일만 한다.
보유·이전에는 아무 제한이 없어 운영자가 사용자 잔고에 개입할 수단이 없다."

**M2** — "발행사가 자산 등록·평가를, 심사 담당자가 KYC 승인·취소를 맡는다(서로 다른 계정).
승인된 계정만 보유·수신할 수 있다. 운영자는 사용자 잔고를 직접 움직일 수 없고, 자격을
취소하면 이후 이전이 막힐 뿐 이미 보유한 수량은 그대로 남는다."

**M3** — "M2에 더해, 법원·감독기관 명령이나 지갑 분실 신고가 있을 때 집행 담당자가 동결·
강제이전·복구를 수행할 수 있다. 집행은 사유를 남겨야 하고 심사 담당자와 서로 다른 두 사람의
승인이 모여야 실행된다. 중대한 사고 시 서비스 전체를 일시정지하되 열람은 계속 가능하다.
매 동기화마다 온체인 총량과 장부 총량을 대사해 초과분을 감시한다."

## 3. 판정 치트시트 (정본: 프롬프트 §5.5)

| 개입 | (a) 운영데이터 | (b) 자격판정 | (c) 보유자자산 | (d) 서비스전체 |
|---|---|---|---|---|
| M1 | ✅ | | | |
| M2 | ✅ | ✅ | | |
| M3 | ✅ | ✅ | ✅ | ✅ |

`M0`(배포 후 특권 함수 없음)은 표에 없다 — 평가 갱신·수익 예치·자산 추가가 하나도 없는
**완전 고정** 구성에서만 성립하고, 그래서 질의 옵션으로도 내놓지 않는다. "운영자 없음"이라는
답은 M0이 아니라 **M1**로 받는다.

**강제 규칙** — §5 축1이 "제약 필요"면 **최소 M2**(승인 주체 없는 화이트리스트는 빈 목록이다).
(c) 채택이면 **M3**이고 `ENFORCER_ROLE`은 `COMPLIANCE_ROLE`과 **다른 계정**이어야 한다.
(c) 미채택이면 ERC-7943 함수는 구현하되 **`ENFORCER_ROLE` 보유자를 두지 않고** 그 선택을 기록한다.

## 4. 역할 치트시트 (정본: 프롬프트 §6.4)

`DEFAULT_ADMIN`(부여·회수만) · `REGISTRAR`(자산) · `VALUER`(평가) · `DISTRIBUTOR`(분배) ·
`COMPLIANCE`(자격) · `ENFORCER`(동결·강제이전·복구, M3) · `PAUSER`(정지, M3).

M2/M3는 anvil 계정에 **실제로 나눠 부여**한다. 한 주소에 몰린 채로 M2/M3을 보고하지 않는다.

## 5. 왜 이렇게 정했나 (조사 근거 · 2026-07 확인)

### ERC-7943을 고르면 관리자 기능은 이미 존재한다

`forcedTransfer`·`setFrozenTokens`는 **인터페이스 필수 함수**이고, 스펙은 접근 제한을
`"MUST restrict access to sensitive functions"`라고만 요구하며 방식을 구현자에게 위임한다.
그래서 **판정을 생략하면 "배포자가 전부 갖는다"가 기본값이 된다.** 이것이 M 축을 §5와
나란히 둔 이유다. (https://eips.ethereum.org/EIPS/eip-7943)

### 직무 분리의 원형 — ERC-3643 Owner / Agent

T-REX는 **Owner**(에이전트 임명·해임, 레지스트리·컴플라이언스 바인딩, `pause`)와
**Agent**(`mint`/`burn`, `forcedTransfer`, `setAddressFrozen`/`freezePartialTokens`,
`recoveryAddress`)를 가른다 — **설정하는 자리와 집행하는 자리를 분리**한다는 발상이다.

우리는 여기서 한 단계 더 나눠 `COMPLIANCE`(자격 등재)와 `ENFORCER`(강제이전·동결)를 가른다.
**T-REX에서는 둘 다 Agent 권한이므로 이것은 표준의 재현이 아니라 확장이다** — 자격을 주는 손이
잔고도 움직일 수 있으면 승인 조작과 자산 이동이 한 계정에서 끝난다. 지갑 분실 복구가
표준 기능으로 들어가 있다는 점은 그대로 가져왔다. (https://eips.ethereum.org/EIPS/eip-3643)

### 이번 범위에 넣지 않은 것 — Centrifuge / AccessManager

Centrifuge는 모든 컨트랙트가 `Auth`(ward)를 상속하고 불변 `Root`가 단일 권한 허브가 되며,
Guardian(Safe + Zodiac Delay 24h)과 Root 타임락 48h를 합쳐 **총 72시간 지연**을 건다.
OpenZeppelin `AccessManager`도 역할별 실행 지연과 취소 guardian을 내장한다.
둘 다 **단일 서비스·소수 컨트랙트 규모에는 과하고**, 지연·취소 계층은 운영 조직이 생긴 뒤의 문제다.
그래서 `AccessControl` + `Ownable2Step`으로 두고 **승격 경로만 README에 문서화**한다.
(https://docs.centrifuge.io/developer/protocol/security/ ·
https://docs.openzeppelin.com/contracts/5.x/access-control)

### 백오피스를 직무 단위로 가르는 이유 — 실무 분업

Securitize는 transfer agent(명부·기업행위), broker-dealer(발행·투자자 온보딩),
fund administrator(NAV·분배·보고)를 **서로 다른 규제 역할**로 수행한다. 기능 목록이 아니라
직무로 탭을 가르면, 지금은 한 사람이 다 하더라도 나중에 사람이 늘 때 **권한만 옮기면 된다.**

### 국내 제도가 요구하는 관리 행위 (코퍼스 근거)

통과된 「주식·사채 등의 전자등록에 관한 법률」 개정 대안 —

| 조문 | 내용 | 설계 반영 |
|---|---|---|
| 제19조의2 | 발행인계좌관리기관 등록요건: 자기자본 10억 이상, **권리자 보호가 가능한 인력·전산설비**, 이해상충방지체계, 임원 요건 | 운영은 개인 EOA 하나가 아니라 **조직 기능**이라는 전제 → M2 직무 분리 |
| 제23조의2 | 발행인계좌관리기관은 **분산원장만** 이용. 기준 위반 시 **1년 이하 징역·3천만원 이하 벌금**(제73조) | 오프체인 장부를 진실로 두는 설계 금지 → §4.3 경계 유지 |
| 제42조의2 | **초과분 해소**·전자등록 안정성 확보를 위한 재원 적립·관리 의무 | **§8.5 총량 대사**를 M3 1급 기능으로 |
| 제23조의3 | 분산원장 특성을 고려한 개인신용정보 파기의무 특례 | PII 온체인 금지(§4.6)의 법적 근거 |

실제 조각투자 서비스 투자설명서도 "계좌관리기관과 거래내역을 정산하고 **보유·발행 총량을
검증**"하는 절차와 **시차·오류로 인한 일시적 권리관계 불일치 위험**을 위험요소로 적는다.
대사 화면은 그 절차가 사는 자리다.

> 조회: `make -C data-platform query Q="발행인계좌관리기관 요건"` ·
> `Q="총량관리 초과분 해소 권리자 보호"` (컬렉션 `토큰증권법안원문`)

## 7. 자주 틀리는 것

- **역할 상수만 만들고 전부 배포자에게 부여** — 분리했다고 보고하지 않는다. 실제로 나눠 준다.
- **`audit_log`를 스키마에만 두고 아무도 쓰지 않음** — 없는 것만 못하다. 관리자 경로의
  모든 쓰기가 한 행을 남겨야 한다.
- **`ENFORCER`와 `COMPLIANCE`가 같은 계정** — M3에서 이건 4-eyes가 아니라 1-eye다.
- **상품 추가 경로를 축3과 다르게 만듦** — D1이면 `assetId` 발급, D2면 팩토리 배포다.
  둘 중 무엇인지는 **Q7로 사용자에게 물어 정한다**(`issuance-unit.md`). 관리자 화면에
  배포 버튼이 있어야 하는지도 거기서 갈린다.
- **운영자 상품 목록 없이 투자자 카탈로그를 재사용** — 투자자 화면에는 "살 수 있는 것"만 뜨므로
  초안·마감·청산 상품이 운영자 눈에서 사라진다.
- **발행 한도를 비워 둔 채 대사를 켬** — 기준선이 없으면 초과분을 잡을 수 없다. 상장 시 확정한다.
- **온체인 멀티시그·타임락을 새로 구현** — 이번 범위 밖이다. 오프체인 2서명으로 끝낸다.
- **관리자 화면을 메인 내비에 노출** — §4.1 위반. 권한 없으면 경로 자체가 보이지 않아야 한다.
- **강제이전을 burn+mint로 구현** — 총량이 흔들려 대사가 깨진다. 이전은 이전이어야 한다.
- **사유 없는 집행** — `reasonHash` 없이 실행되는 경로를 남기지 않는다.
