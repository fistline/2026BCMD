# ST Service dApp Generator

`gen-apps/ST_SERVICE_DAPP_PROMPT.md`는 Security Token(RWA) 서비스 dApp을 통째로 생성하는
대형 프롬프트다. §2의 4개 설정(Token Standard=AUTO / chain / MockUSDC / SQLite)은 이미 고정돼 있고,
**§1의 Q1~Q5(Service Vision)만 사람이 채워야 한다.** 이 스킬의 임무는 Q1~Q5를 **전문가 수준으로
확정**한 뒤 **프롬프트 전체를 실행**하는 것이다.

핵심 원칙: 이 프롬프트의 산출물 품질은 §1의 서술 품질에 전적으로 종속된다. 표준 판정(§5),
화면 설계(§9), 컨트랙트 표면(§6)이 모두 §1에서 역산된다. 그래서 사용자의 한 줄짜리 답을
**그대로 붙여 넣지 않는다.** dApp 전문가 관점에서 구현을 유도할 수 있을 만큼 구체적으로 확장한다.

---

## 이 스킬이 하는 일 (한눈에)

```
1. 템플릿 로드 → Q1~Q5 중 무엇이 비었는지 판정
2. 대화에 이미 있는 정보로 먼저 채운다 (중복 질문 금지)
3. 남은 항목 질의 — 사용자에게 서비스 아이디어를 묻되,
   답이 없거나 부적절하면 5가지 완성형 서비스 예시를 제시해 고르게 함
4. 확정된 답을 dApp 전문가로서 Q1~Q5 각 항목에 맞게 확장·프롬프트화해 기입
5. 채워진 §1 초안 + 추론된 표준(S1~S6)을 한 번에 보여주고 확인
6. **전용 하위 폴더 `gen-apps/<service-slug>/`를 먼저 생성**하고, 채운 프롬프트 사본을 그 안에 저장
   (원본 템플릿은 보존)
7. 그 폴더를 프로젝트 루트로 삼아, 프롬프트의 PHASE 0~5를 게이트 순서대로 실행 → dApp 완성
   (모든 산출물이 이 폴더 안에서만 생성된다. 레포 루트에 흩뿌리지 않는다.)
```

## PHASE A — 로드 & 결손 판정 (항상 먼저)

1. `gen-apps/ST_SERVICE_DAPP_PROMPT.md`를 읽는다.
2. Q1~Q5 각 항목이 `[ 내용작성필요 ]`(또는 빈칸/placeholder)인지, 실제 서술로 채워졌는지 판정한다.
3. **사용자가 이번 대화에서 이미 말한 서비스 설명을 먼저 매핑한다.** 사용자가 "부동산 조각투자
   만들어줘"라고 했다면 Q1의 실마리는 이미 있다. 있는 정보로 채울 수 있는 항목은 질문하지 않는다.
4. §2의 4개 설정은 고정이므로 **묻지 않는다.** 오직 Q1~Q5만 대상이다.

> 이미 채워진 템플릿을 받았거나 사용자가 5개 항목을 모두 서술했다면 → PHASE B를 건너뛰고
> PHASE C(확장·정제)로 간다. 없는 것만 묻는다.

---

## PHASE B — 질의 (결손이 있을 때만)

`references/intake.md`의 질의 프로토콜을 따른다. 요지:

### B-1. 한 번에 묻는다

빈 항목이 여럿이어도 **한 번의 질의로 몰아서** 묻는다. 항목을 하나씩 쪼개 되묻지 않는다.
Q1~Q5는 하나의 일관된 서비스를 서술하므로, 보통은 **"무엇을 만들고 싶은가?"** 한 질문이면
나머지는 전문가가 역산할 수 있다.

### B-2. 답이 없거나 부적절하면 → 5가지 예시 제시 (필수)

다음 중 하나에 해당하면 `references/archetypes.md`의 **5가지 완성형 서비스 예시**를 제시하고
사용자가 고르게 한다. `AskUserQuestion`으로 5개를 옵션화하면(자동 제공되는 "Other"로 자유 입력 가능)
"기회를 주는 열린 질문"과 "5가지 예시 제시"가 한 번에 처리된다.

- 사용자가 답을 하지 않거나 "아무거나", "알아서" 류로 응답
- RWA/증권형 서비스로 성립하기 어렵거나(예: 단순 To-Do 앱), 이 프롬프트 범위를 벗어남
- 서로 모순되거나 표준 판정(축1/축2)을 가를 수 없을 만큼 모호함

5개는 **표준이 서로 다르게 나오도록** 다양하게 구성돼 있다(S2/S3/S4/S6, 볼트/분배/로열티 등).
사용자가 그래도 결정하지 못하면, 가장 단순하고 시연이 명확한 후보 **하나를 추천**하고
그 이유를 한 줄로 말한 뒤 진행한다. 무한정 되묻지 않는다.

### B-3. 부분 답변

사용자가 일부만 답하면 답한 것만 반영하고, 남은 항목은 PHASE C에서 전문가 추론으로 메운다.
단, **표준을 뒤집는 항목(Q4 자격 제한)** 이 불명확하면 그 항목만은 명시적으로 확인한다.
Q4가 모호할 때는 §5.판정우선순위에 따라 **더 단순한 쪽(제약 없음)** 을 기본값으로 두되,
그 가정을 사용자에게 한 줄로 알린다.

## PHASE C — 확장 & 프롬프트화 (이 스킬의 핵심)

확정된 답을 `references/field-guide.md`의 항목별 루브릭에 따라 확장한다. 사용자의 축약된 답을
**구현을 유도하는 서술**로 바꾸는 단계다. 요지:

- **Q1** — 누가·무엇을·왜의 한 문장. 날카롭고 구체적으로.
- **Q2** — 처음 방문 → 목적 달성까지의 여정을 사용자의 언어로 순서화(탐색→온보딩→참여→보유/수익→이전/회수).
- **Q3** — 자산 클래스와, 가치·수익이 사용자에게 돌아오는 경로(임대수익/시세차익/배당/로열티/환매). 정산은 MockUSDC.
- **Q4** — 자격 제한을 명시(KYC/적격투자자/락업/관할/보유상한) 또는 "없음". **이 한 줄이 ERC-7943 여부를 가른다.**
- **Q5** — 핵심 화면과 상호작용, 상태 표시, 지갑 미연결 방문자가 보는 것.

확장 시 반드시 지킬 것:

1. **§5 표준 추론과 정합하게 쓴다.** Q3(자산 다중성=축2)과 Q4(이전 제약=축1)가 표준을 결정하므로
   이 둘은 애매하지 않게 서술한다. 확장 결과로 S1~S6 중 어디로 판정되는지를 스스로 확인한다.
2. **없는 사실을 지어내지 않는다.** 발행사명·수치·평가액 등 사용자가 안 준 값은 만들지 말고,
   시연용 시드로 채울 자리표시임을 서술에 남긴다(예: "로컬 시드로 3개 자산 예시 등록").
3. **컨트랙트 함수명이 아니라 서비스 언어로 쓴다.** mint/burn이 아니라 "발행 신청/청약".
4. 확장 결과는 프롬프트가 그대로 소비할 수 있는 **완결된 문단**이어야 한다. `TODO`/`...` 금지.

## PHASE D — 확인 게이트 (실행 직전 1회)

확장한 Q1~Q5 전문과 함께 다음을 **간결하게** 제시하고 사용자 확인을 받는다:

- 채워진 Q1~Q5 초안(각 항목 실제 문단)
- 이로부터 추론된 **표준(S1~S6)** 과 부가 확장(있으면), 그 근거 한 줄
- **산출 폴더**: `gen-apps/<service-slug>/` — 이 폴더가 곧 Scaffold-ETH 2 프로젝트 루트이며,
  생성되는 모든 것(컨트랙트·프론트·DB·문서)이 이 안에서만 만들어진다. 슬러그도 함께 보여준다.

전체 생성은 규모가 크고 비용이 있으므로 **이 지점에서 한 번만** 확인한다. "그대로 진행"이면
PHASE E로 간다. 사용자가 특정 항목을 고치라고 하면 해당 항목만 다시 확장한다.

> 확인은 한 번으로 끝낸다. 매 항목마다 승인을 받지 않는다. 사용자가 처음부터 "묻지 말고
> 알아서 끝까지"라고 했다면 이 게이트도 요약 통지로 갈음하고 바로 실행한다.

## PHASE E — 실행 (전용 하위 폴더 안에서만)

> **핵심: 코드를 한 줄 만들기 전에 전용 하위 폴더부터 만들고, 이후 모든 작업을 그 안에서만 한다.**
> 프로젝트 파일을 레포 루트나 `gen-apps/` 바로 아래(템플릿·스킬과 같은 층)에 흩뿌리지 않는다.
> 모든 산출물은 반드시 `gen-apps/<service-slug>/` 폴더 안에 둔다.

**E-0. 프로젝트 폴더 생성 (제일 먼저)**

1. **슬러그 결정** — Q1에서 서비스명을 kebab-case ASCII로 만든다(예: 부동산 임대수익 조각투자 →
   `real-estate-rental-shares`, 탄소배출권 마켓 → `carbon-credit-market`). 공백·한글·특수문자는
   하이픈/음역으로 정리한다. **예약어** — `st-service-dapp`, `filing-to-dapp`(스킬 폴더)은
   슬러그로 쓸 수 없다. 충돌하면 `-app` 등 접미사를 붙이고 통지한다.
2. **폴더 생성** — `gen-apps/<service-slug>/`를 만든다. 이 폴더가 **Scaffold-ETH 2 프로젝트 루트**다.
   - 같은 슬러그 폴더가 이미 있고 **동일 서비스의 재생성**이면 그 폴더를 재사용한다(멱등).
   - **다른 서비스인데 슬러그가 충돌**하면 `-2`, `-3` 접미사를 붙이고 그 사실을 통지한다.
3. **원본 템플릿은 수정하지 않는다**(재사용 자산). Q1~Q5를 채운 사본을
   `gen-apps/<service-slug>/PROMPT_FILLED.md`로 저장한다.
4. 이후 프롬프트의 모든 산출물(`DECISION.md`, `ASSUMPTIONS.md`, `README.md`, `packages/…`,
   `package.json` 등)은 **이 폴더 안 경로**로 생성한다. `yarn dev`도 이 폴더에서 실행된다.

산출 폴더 구조:

```
gen-apps/
├── ST_SERVICE_DAPP_PROMPT.md    # 원본 템플릿 (건드리지 않음)
├── st-service-dapp/             # 이 스킬
└── <service-slug>/             # ← 생성되는 dApp 프로젝트 루트 (SE-2 모노레포)
    ├── PROMPT_FILLED.md         # Q1~Q5 채운 프롬프트 사본
    ├── DECISION.md              # PHASE 0 산출
    ├── ASSUMPTIONS.md
    ├── README.md
    ├── package.json             # yarn dev 오케스트레이션
    └── packages/
        ├── foundry/             # 컨트랙트·테스트·배포
        └── nextjs/              # 프론트·Route Handlers·SQLite
```

**E-1. 프롬프트 실행**

`PROMPT_FILLED.md`의 지시를 **그대로, 순서대로 따른다.** 프롬프트는 자체 실행 계약을 갖는다:
   - PHASE 0 설계(`DECISION.md`) → 게이트 0
   - PHASE 1 컨트랙트(`forge build`/`forge test`) → 게이트 1
   - PHASE 2 배포·시드(`deployedContracts.ts`) → 게이트 2
   - PHASE 3 데이터 계층(마이그레이션·인덱서·Route Handlers) → 게이트 3
   - PHASE 4 프론트엔드 → 게이트 4
   - PHASE 5 §13 인수 검증 → 보고

**각 게이트를 통과한 뒤에만** 다음으로 넘어간다. 프롬프트의 §11 Output Format Contract와
§12 Quality Gates를 준수한다. §1이 이미 완결됐으므로 **후속 질문은 하지 않는다**(프롬프트 §4.5).
경로는 항상 `gen-apps/<service-slug>/` 기준 상대경로로 만든다(예: SE-2 컨트랙트는
`packages/foundry/contracts/...`).

이 단계는 길다. 프롬프트가 요구하는 게이트 검증(빌드/테스트/배포/여정 완주)을 실제로 수행하고,
**검증하지 않은 항목을 통과로 보고하지 않는다.**

## 이 스킬이 지켜야 할 것

- **§1을 완결시키는 것이 유일한 목적.** 완결 후엔 프롬프트에 온전히 위임하고 새 질문을 만들지 않는다.
- **한 번에 묻고, 5가지 예시로 막힌 곳을 뚫는다.** 항목별로 질질 끌지 않는다.
- **확장하되 지어내지 않는다.** 서술은 풍부하게, 사실(수치·고유명)은 시드 자리표시로.
