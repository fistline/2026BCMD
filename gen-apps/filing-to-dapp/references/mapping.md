# 매핑 규칙: 증권신고서 → dApp Q1~Q5 + 표준 (PHASE 3)

증권신고서의 사실을 dApp §1(Service Vision)과 토큰 표준으로 옮긴다. **사실은 보존하고, 서비스 언어로
표현하며, 없는 값은 지어내지 않는다.**

---

## 매핑 원칙

1. **사실 보존** — 신고서의 F(수치·일자·상대방·평가결과)는 그대로 옮기되, PII·계약상대방 실명은 온체인 제외.
2. **서비스 언어** — "모집·청약·전매제한"을 사용자 화면 언어로. 단, 규제상 정확성은 잃지 않는다.
3. **미확정 존중** — 신고서의 `[미확정]`은 매핑에서도 미확정. 시연이 필요하면 "로컬 시드" 자리표시.
4. **표준은 잠정** — 여기서 산출한 S1~S6는 st-service-dapp §5로 **재확인**한다(이 매핑이 근거 자료).

## 증권 유형 → 구조·표준 상관

sto-filing의 유형 판정이 dApp 구조의 출발점이 된다.

| 증권 유형 | 자산·표준 경향 | 자금흐름(§6.3) | 게이트 |
|---|---|---|---|
| **투자계약증권** (공동사업·공유지분) | 대개 여러 회차/물건 계속 발행 → **다중 대체가능 + 전매제한 → S4**. 단일 프로젝트 1건이면 **S2**. 미술품 원본 등 1물1권이면 **S6** | `assetId`별 청약·환매 매니저 + 분배 pull | 사전 인허가 불요(신고서만) → 통상 진행 |
| **비금전신탁 수익증권** (혁신금융 특례) | 수익증권=대체가능 지분. 신탁재산 다수면 **S4**, 단일이면 **S2** | 신탁 수익 분배 pull, 청약·환매 매니저 | **혁신금융서비스 지정 없으면 발행 불가 → 중단**(gate.md) |
| **집합투자증권** | 자금을 모아 운용하는 풀 → ERC-4626 볼트 후보(S1/S2 한정) | 동기 볼트(deposit/redeem) | **집합투자업 인가 없으면 무인가 영업 → 중단**(gate.md) |

> 대부분의 조각투자는 **대체가능 지분 + 전매제한**이라 **S4(ERC-6909+7943)** 로 수렴한다.
> S2는 단일 자산, S6는 개별 고유 1물1권일 때만.

## 축2 — 기초자산 다중성 판정 (→ 표준의 자산축)

신고서의 기초자산 서술에서 읽는다.

- **단일 자산 1종**, 추가 발행 계획 없음 → 단일 대체가능 → **S1/S2** (또는 1물1권이면 S5/S6)
- **여러 물건/회차를 계속 상장·추가** → 다중 대체가능 → **S3/S4**
- **개별 고유 자산 1물1권** (특정 부동산 1건의 소유권, 미술품 원본) → **S5/S6**

애매하면 **더 단순한 쪽(단일)** 을 택하고 그 가정을 통지한다(§5 우선순위 승계).

## 축1 — 자격·전매제한 판정 (→ ERC-7943 여부, 가장 중요)

신고서의 **모집·청약·전매제한** 조항이 dApp Q4와 온체인 TransferPolicy로 직결된다.

| 신고서 조항 | → Q4 서술 | → 온체인 구현 |
|---|---|---|
| 전매제한 기간(보호예수·락업) | "발행 후 N일 이전 제한" | TransferPolicy lockup, `canMove` 차단 |
| 적격투자자·전문투자자 한정 | "적격투자자만 보유·수신" | WhitelistPolicy(적격 판정), `canReceive` |
| 청약 자격(일반투자자 한도 등) | "청약 자격 요건" | 온보딩 심사 → 판정결과 온체인 |
| 관할·거주지 제한 | "특정 관할 제외" | `canReceive` 차단 목록 |
| 1인 보유한도(모집 규정) | "1인 보유상한" | 보유상한 체크 |
| 제한 조항이 전혀 없음(희귀) | "없음" | 표준 ERC-20 계열, **ERC-7943 미적용** |

> **규칙**: 위 중 하나라도 있으면 축1 "제약 필요" → **ERC-7943(uRWA) 확장**. 증권신고서로 발행되는
> 증권은 거의 항상 여기에 해당한다. 실명·서류는 온체인 금지, 온체인엔 **판정 결과(bool/해시)만**(gate.md).

## 항목별 Q1~Q5 매핑

| dApp 항목 | 신고서에서 가져오는 것 |
|---|---|
| **Q1** (한 문장) | 발행사 + 증권명 + 기초자산 + 발행 목적 → "누가 무엇을 하러 오는가". 발행사명은 서비스 카피에 사용하되 대표자 개인정보는 배제 |
| **Q2** (여정) | 모집 절차(청약공고→청약→배정→납입) + 유통 제한 → 탐색·온보딩(자격심사)·청약·보유/수익·이전(제약) 여정 |
| **Q3** (자산·수익) | 기초자산 + 다중성(축2) + 수익구조(임대/배당/이자/상환/매각차익)와 분배주기. 정산 MockUSDC |
| **Q4** (자격 제한) | 전매제한·적격투자자·청약자격·보유한도(축1). 없으면 "없음" |
| **Q5** (화면) | 위험요소·투자자 보호 고지 → 화면 고지 문구, 이전 차단 사유 표시, 사전검증 배너. 다크 미니멀 |

## 수익구조 → 구현 매핑

| 신고서 수익구조 | dApp 구현 |
|---|---|
| 정기 분배(임대료·배당·이자) | PeriodicPull Distribution, 주기별 예치 + `claim` 화면 |
| 만기 원리금 상환 | 상환 매니저 + `claim`, 만기 캘린더 UI. 부도 가능성 고지 |
| 매각·청산 시 일시 분배 | 청산 분배(pull), 매각 정산 카드 |
| 풀 운용 손익(NAV) | ERC-4626 볼트(S1/S2 한정) — 단 집합투자 게이트 주의 |

**분배는 항상 pull**(§4.7). 보유자 순회 push 금지.

## 출처 결속 (provenance) 매핑

신고서와 dApp을 **공유 슬러그 + 문서 해시**로 잇는다. dApp이 이미 갖춘 훅(§6.2 AssetRegistry,
§8.2 asset_documents)을 실제 신고서로 채우는 것이다. 새 컨트랙트 필드를 만들지 않는다.

| 결속 | 값 | 배치 |
|---|---|---|
| **슬러그** | 신고서 폴더명(`gen-docs/st_prospectus/<slug>/`) 재사용. 없으면 발행사+증권명 kebab-case ASCII. 예약어(`st-service-dapp`, `filing-to-dapp`, `sto-filing`)와 충돌 시 접미사 강제 | 양쪽 폴더 공유 키 |
| **documentHash** | 신고서 파일의 keccak256 해시 | 온체인 `AssetRegistry.documentHash` |
| **metadataURI** | **공개용 메타**(발행사·증권명·요약, PII 없음) 위치 | 온체인 `AssetRegistry.metadataURI` |
| **asset_documents 시드** | 발행사·증권명·작성일·유형판정·신고서 경로·documentHash | 오프체인 DB(온체인 해시와 대조) |
| **SOURCE.md** | 신고서 경로 + 생성시점 해시 + 유형판정 + 슬러그 | dApp 루트 파일 |

**정정신고서 감지가 공짜로 생긴다**: 신고서가 바뀌면 파일 해시가 달라진다 → `asset_documents`의
documentHash가 온체인/신고서와 불일치 → "정정 반영 필요" 신호. 이게 링크를 두는 실질 목적이다.

**PII 주의**: documentHash는 해시일 뿐이라 원문 전체를 해시해도 안전하다(원문은 오프체인 보관).
그러나 `metadataURI`가 가리키는 것은 **PII 없는 공개 메타**여야 한다 — 신고서 원문을 그대로 가리키지 않는다.

## 표준 산출 요약 (PHASE 3 자기점검)

1. 유형 상관표 + 축2(다중성) + 축1(전매제한) → S1~S6 하나로 확정되는가?
2. 부가 확장(ERC-2612/4626/Votes)은 **신고서에 근거가 있을 때만**. 집합투자=볼트라도 인가 게이트 우선.
3. 애매한 축은 더 단순한 표준을 택하고 가정을 통지.
4. 산출한 표준·근거를 st-service-dapp PHASE C로 넘겨 §5로 재확인.

산출 예: "투자계약증권 + 임대부동산 물건별 상장(다중) + 적격투자자·전매제한 → **S4(ERC-6909+7943)**,
분배는 PeriodicPull, 부가 확장 없음."
