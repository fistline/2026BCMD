# 증권신고서 → dApp 브리지

증권신고서와 서비스 dApp은 **같은 사실을 서로 다른 계층에서 표현**한다. 신고서에 이미 dApp
§1(Q1~Q7)의 답이 대부분 들어 있으므로, 이 스킬은 신고서를 dApp 사양으로 **역매핑**해
`st-service-dapp` 생성으로 이어붙인다.

**설계 원칙 — 복제하지 않는다.** 문서 작성은 `sto-filing`이, dApp 생성은 `st-service-dapp`이
그대로 한다. 이 스킬이 새로 담는 것은 **① 신고서→Q1~Q7+표준·운영모델 매핑, ② 게이트 승계·PII 경계**뿐이다.

```
sto-filing  →  [이 스킬: 매핑 + 게이트 승계]  →  st-service-dapp (PHASE C~E)
(문서)         (신고서 → Q1~Q7 + 표준 + 운영모델)     (확장 → 확인 → 실제 생성)
```

핵심 통찰:
- **전매제한 → 표준 자동 확정.** 신고서로 발행되는 토큰은 규제상 거의 항상 전매제한이 있어
  축1이 "제약 필요"로 수렴 → **S2/S4/S6(ERC-7943)** 로 표준 판정이 사실상 자동화된다.
- **신고서의 자격요건 = 온체인 TransferPolicy.** 적격투자자·전매제한이 그대로 `canSend/canReceive`가 된다.
- **발행 불가 증권은 dApp도 막는다.** sto-filing이 중단시킨 건 이 스킬도 중단한다(§ PHASE 2).

---

## 이 스킬이 하는 일 (한눈에)

```
1. 진입 모드 판정 — 이미 쓴 신고서가 있는가(A) / 처음부터인가(B)
2. (B라면) sto-filing을 먼저 돌려 신고서 + 유형판정을 확보
3. 게이트 승계 — 발행 불가·미확정·저신뢰 판정이면 여기서 중단 (references/gate.md)
4. 매핑 — 신고서 → Q1~Q7 + 표준(S1~S6) + 운영 모델(M0~M3) 초안 생성 (references/mapping.md)
5. 핸드오프 — st-service-dapp의 PHASE C(확장)→D(확인)→E(실제 생성) 실행
   (신고서로 Q1~Q7이 채워졌으므로 st-service-dapp의 질의(PHASE B)는 통째로 건너뛴다 —
   5예시도, 운영 질의도 하지 않는다)
6. 출처 결속 — 신고서와 dApp을 공유 슬러그·문서해시로 잇는다(SOURCE.md, documentHash, asset_documents)
```

## 진입 모드

| 모드 | 조건 | 동작 |
|---|---|---|
| **A. 이어받기** (주 모드) | 이미 작성된 증권신고서가 있음(파일 경로·붙여넣기·`gen-docs/st_prospectus/` 산출물) | PHASE 1부터 |
| **B. 연속** | 신고서가 아직 없음 ("신고서부터 써서 앱까지") | 먼저 `sto-filing`을 완주(판정→작성→자기심사)한 뒤 그 산출물로 PHASE 1 |

모드 B에서는 `gen-docs/st_prospectus/sto-filing/SKILL.md`를 로드해 그 스킬을 **그대로 수행**한다.
이 스킬은 sto-filing의 판정·게이트·산출을 재구현하지 않는다.

---

## PHASE 1 — 신고서 수집·정규화

1. 증권신고서(초안/확정)와, 있으면 **증권유형판정서**를 확보한다. 없으면 신고서 본문에서 유형을 역판정한다.
   신고서는 보통 `gen-docs/st_prospectus/<slug>/`에 있다(구버전은 loose). 이 `<slug>`가 dApp과의 공유 키다.
2. 매핑에 필요한 항목을 신고서에서 읽어낸다: **증권 유형 / 기초자산과 다중성 / 수익구조·분배주기 /
   청약·모집 구조 / 전매제한·적격투자자·보유한도 / 발행사·증권명 / 위험요소 /
   운영 주체와 권리자 관리·사고 시 조치 조항**. (상세는 `references/mapping.md`)
3. 신고서에 `[미확정]`·`[발행사 확인 요망]`으로 남은 항목을 목록화한다. **없는 값을 지어내지 않는다**
   (sto-filing의 F/N/J 규율 승계). 표준을 가르는 자리(Q3 다중성·Q4 제약)의 미확정은 PHASE 2에서 다룬다.

---

## PHASE 2 — 게이트 승계 (중단 판정)

`references/gate.md`를 적용한다. 아래에 해당하면 **dApp 생성으로 넘어가지 않는다.**

- sto-filing이 중단시킨 사유(집합투자증권→인가 필요 / 미지정 신탁→발행 불가 / 미인가 수탁자 / 판정 신뢰도 낮음)
- 표준을 결정하는 항목(기초자산 다중성=축2, 전매제한·자격=축1)이 `[미확정]`이라 판정이 뒤집힐 수 있음
- 신고서와 사용자 진술이 모순

중단이라고 대화를 끝내지 않는다. **무엇을 바꾸면 진행 가능한지**를 구체적으로 제시한다(sto-filing 태도 승계).
표준을 가르는 미확정 한둘만 남았으면 그 항목만 확인하고, 나머지는 진행한다.

---

## PHASE 3 — 매핑 (신고서 → Q1~Q7 + 표준 + 운영 모델)

`references/mapping.md`의 매핑표대로 신고서 사실을 dApp §1으로 옮긴다. 산출:

- **Q1~Q7 초안** — 신고서 사실에 근거한 완결 문단. 컨트랙트 함수명이 아니라 서비스 언어로.
- **표준(S1~S6) 잠정 판정** — 유형·다중성·전매제한에서 산출한 근거와 함께.
- **발행 단위(D1/D2) 판정** — 신탁 구조와 모집 범위에서 **읽는다**(추론이 아니라 독해).
  신고서로 안 읽히면 dApp Q7로 **사용자에게 확인**한다. D2면 상품마다 컨트랙트가 배포된다.
- **운영 모델(M0~M3) 잠정 판정** — 신고서 기반은 **M3에서 시작해 근거 없는 권한을 덜어낸다.**
  각 권한에 **근거 조항**을 붙인다(집행 사유가 나중에 빈칸으로 남지 않게).
- **PII 경계 적용** — 실명·연락처·재무 등 개인정보/계약상대방은 온체인에서 제외하고, 자격은 판정결과(bool/해시)만.
- **미확정 처리** — 신고서에서 못 채운 값은 "로컬 시드로 채움" 자리표시로 남기고 지어내지 않는다.

이 초안은 st-service-dapp 프롬프트의 `[ 내용작성필요 ]` 자리에 그대로 들어간다.

---

## PHASE 4 — 핸드오프 (st-service-dapp 실행)

`gen-apps/st-service-dapp/SKILL.md`를 로드해 그 스킬을 **PHASE C부터** 수행한다.

**슬러그는 신고서와 공유한다.** 신고서가 `gen-docs/st_prospectus/<slug>/`에 있으면 그 폴더명을 dApp
슬러그로 **그대로 재사용**하고, loose/구버전이면 발행사+증권명에서 같은 규칙으로 파생한다.
결과적으로 `gen-docs/st_prospectus/<slug>/`(문서) ↔ `gen-apps/<slug>/`(dApp)가 같은 키로 묶인다.

1. **PHASE C(확장)** — PHASE 3의 Q1~Q7 초안을 dApp 전문가 관점에서 확장·정제.
   §5 표준 추론 + §5.5 운영 모델과 정합 확인.
   신고서로 이미 채워졌으므로 **st-service-dapp의 질의(PHASE B)는 하지 않는다**(5예시·운영 질의 모두).
2. **PHASE D(확인)** — 채운 Q1~Q7 + 추론 표준 + **운영 모델과 역할 배정** + 산출 폴더
   (`gen-apps/<slug>/`) + **매핑 근거**(신고서 어느 항목 → 어느 Q, 어느 조항 → 어느 권한)를 한 번 확인.
3. **PHASE E(생성)** — `gen-apps/<slug>/`를 만들고 프롬프트 PHASE 0~5를 게이트 순서대로 실행.
   생성 중 **출처 결속(provenance)** 을 함께 심는다(상세: `references/mapping.md`):
   - `AssetRegistry.documentHash` = 신고서 파일 해시(keccak256), `metadataURI` = **공개 메타**(PII 없는 버전) 위치
   - `asset_documents` 시드 = 발행사·증권명·작성일·유형판정·신고서 경로·해시 (온체인 해시와 대조)
   - dApp 루트에 **`SOURCE.md`** — 신고서 경로 + 생성시점 해시 + 유형판정 + 슬러그
4. 생성물 `README.md`에 다음을 **반드시** 명시한다:
   - 이 dApp은 로컬/테스트넷 **기술 프로토타입**이며, 실제 규제 발행이 아니다.
   - 원본 증권신고서 참조(발행사·증권명·작성일, `gen-docs/st_prospectus/<slug>/`)와 sto-filing 법적 고지 포인터.
   - 온체인에는 자격 **판정 결과만**, 개인정보·법적 원문은 오프체인.
   - **운영자가 가진 권한**(자격 승인·동결·강제이전·복구·정지)과 그 **발동 근거 조항·승인 절차**.
     프로토타입에서는 이 권한들이 로컬 anvil 계정에 배정된다는 사실도 함께 적는다 —
     보유자가 자기 자산에 누가 개입할 수 있는지 모르는 채로 두지 않는다.

## 이 스킬이 지켜야 할 것

- **복제 금지.** 문서는 sto-filing이, dApp은 st-service-dapp이 한다. 이 스킬은 잇기만 한다.
- **게이트를 승계한다.** 발행 불가로 막힌 증권을 dApp으로 만들지 않는다. 막을 땐 대안을 제시한다.
- **사실을 지어내지 않는다.** 신고서의 `[미확정]`은 그대로 미확정. 표준을 가르는 미확정만 확인한다.
- **권한마다 근거 조항을 댄다.** 신고서에 근거가 없는 관리자 권한은 넣지 않고, 있는 권한을
  빼지도 않는다. 근거 없이 붙인 강제이전 권한은 프로토타입에서도 위험하다.
- **개인정보를 온체인에 올리지 않는다.** 자격은 bool/해시만, 실명·재무·서류는 오프체인.
- **프로토타입임을 분명히 한다.** 생성물은 실제 규제 발행이 아니라는 고지를 README에 남긴다.
